# Todo 010: Backend Credit Limit Verification API

**Status:** ⬜ Not started

## Description
Add a **pre-submit** credit limit check for the POS checkout flow. ERPNext core already enforces
credit limits on `Sales Invoice.on_submit()` (`erpnext.selling.doctype.customer.customer.check_credit_limit`,
wired in from `sales_invoice.py:519/745`), and klik_pos does not bypass it — so an over-limit invoice
already fails today via `doc.submit()`. The gap is that this only fires *after* `doc.insert()`,
leaving an orphaned draft Sales Invoice and giving the cashier no warning until the whole Payment
Dialog flow has been filled in.

This todo does **not** reimplement the credit limit / outstanding-balance math. It wraps the
existing core helpers so the frontend can check ahead of time.

## Estimated Time
30-45 minutes (reduced from original 45-60 since no new balance/limit math is needed)

## Files to Change
- `klik_pos/api/sales_invoice.py`

## Implementation Notes
- Implement `check_customer_credit_limit(customer, new_invoice_amount, company)`:
  - Call `erpnext.selling.doctype.customer.customer.get_credit_limit(customer, company)` for the limit.
  - Call `erpnext.selling.doctype.customer.customer.get_customer_outstanding(customer, company)` for
    the current outstanding balance.
  - If `credit_limit > 0` and `current_outstanding + new_invoice_amount > credit_limit`, return
    `{"exceeded": True, "credit_limit":, "current_outstanding":, "new_invoice_amount":, "excess":}`.
  - If `credit_limit` is 0 (unlimited) or within bounds, return `{"exceeded": False, ...same fields}`.
- `@frappe.whitelist() def validate_before_submit(data)`: parses `customer` and the draft's grand
  total from `data` (mirror the parsing already used by `submit_draft_invoice`/`build_sales_invoice_doc`)
  and calls `check_customer_credit_limit`. This is advisory only for UX — actual enforcement stays
  in ERPNext core's `on_submit`, so it can't be bypassed by skipping this pre-check.

## Dependencies
- None

## Acceptance Criteria
- `check_customer_credit_limit` reuses core `get_credit_limit`/`get_customer_outstanding` rather than
  new SQL against `Sales Invoice.outstanding_amount`.
- `validate_before_submit` endpoint correctly exposes this functionality for pre-submission checks.
- Behavior matches what core's `check_credit_limit` would do on submit (same limit source, same
  outstanding-balance source), so the pre-check and the real enforcement never disagree.

## Risks
- Concurrency issues if multiple invoices are submitted simultaneously for the same customer (the
  pre-check can go stale between the check and the actual submit — this is expected and fine since
  core's `on_submit` check is still the real gate).
