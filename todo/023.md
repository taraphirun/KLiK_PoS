# Todo 023: Reconciliation API + Mark-as-Paid Automation

**Status:** ⬜ Not started

## Description
Endpoints that let a human resolve a Delivery Report: confirm the (suggested or manually chosen)
invoice match, reject it, or re-match to a different invoice. On **confirm**, stamp the reconciled
delivery data onto the Sales Invoice (Todo 020 fields) and — if the driver reported payment was
collected — post a Payment Entry to mark the invoice paid.

## Estimated Time
2-3 hours

## Files to Change
- `klik_pos/api/delivery.py` (MODIFY)

## Endpoints
- `@frappe.whitelist() def confirm_delivery_match(report_name, invoice_name=None, mark_paid=None)`:
  - Sets `matched_invoice`, flips `reconciliation_status` → `Confirmed`.
  - Writes `custom_delivery_status`, `custom_delivery_driver`, `custom_delivered_at`,
    `custom_delivery_gps_*`, `custom_delivery_report` onto the Sales Invoice.
  - If `payment_status` is `Paid` or `Partial` (and `mark_paid` not explicitly false): call the
    existing `create_payment_entry(sales_invoice, mode_of_payment, amount_paid)` in
    `klik_pos/api/sales_invoice.py` for the collected amount (full outstanding for `Paid`,
    `amount_collected` for `Partial`; default cash), then store the resulting Payment Entry name on
    the Delivery Report. Also map `completion_status` → `custom_delivery_status`
    (Full → Delivered, Partial → Partially Delivered).
- `@frappe.whitelist() def reject_delivery_match(report_name, reason=None)`:
  - Flips status → `Rejected`; does not touch any invoice.
- `@frappe.whitelist() def rematch_delivery_report(report_name, invoice_name)`:
  - Overrides the suggested match; sets status back to `Suggested` for re-confirmation.

## Acceptance Criteria
- Confirm on an **unpaid** invoice with `payment_status=Paid` produces a submitted Payment Entry,
  invoice `outstanding_amount` drops to 0 (or by `amount_collected` for `Partial`), and the ledger
  balances.
- Confirm with `payment_status=Unpaid` stamps delivery data but posts **no** Payment Entry.
- Confirming an already-`Confirmed` report is a no-op (no double payment) — idempotent.
- Reject and re-match never leave partial writes on the invoice.
- `amount_collected` is validated against outstanding (do not over-allocate).

## Dependencies
- Todo 019, 020, 022
- Reuses `create_payment_entry` (Phase 0/existing code) — do not reimplement.

## Risks
- **Double payment** on re-confirm or race conditions — guard with the `payment_entry` link and
  a status check before posting.
- Partial delivery + partial payment interaction: decide whether `Partially Delivered` still
  allows full payment; document the chosen rule.
- Mode of payment for driver-collected cash must map to a valid Mode of Payment / account.
