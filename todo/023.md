# Todo 023: Reconciliation API + Mark-as-Paid Automation

**Status:** ✅ Done

## Description
Endpoints that let a human resolve a Delivery Report: confirm the (suggested or manually chosen)
invoice match, reject it, or re-match to a different invoice. On **confirm**, stamp the reconciled
delivery data onto the Sales Invoice (Todo 020 fields) and — if the driver reported payment was
collected — post a Payment Entry to mark the invoice paid.

## Estimated Time
2-3 hours

## Files to Change
- `klik_pos/api/delivery.py` (MODIFY)

## Endpoints
- `@frappe.whitelist() def confirm_delivery_match(report_name, invoice_name=None, mark_paid=None)`:
  - Sets `matched_invoice`, flips `reconciliation_status` → `Confirmed`.
  - Writes `custom_delivery_status`, `custom_delivery_driver`, `custom_delivered_at`,
    `custom_delivery_gps_*`, `custom_delivery_report` onto the Sales Invoice.
  - If `payment_status` is `Paid` or `Partial` (and `mark_paid` not explicitly false): call the
    existing `create_payment_entry(sales_invoice, mode_of_payment, amount_paid)` in
    `klik_pos/api/sales_invoice.py` for the collected amount (full outstanding for `Paid`,
    `amount_collected` for `Partial`; default cash), then store the resulting Payment Entry name on
    the Delivery Report. Also map `completion_status` → `custom_delivery_status`
    (Full → Delivered, Partial → Partially Delivered).
- `@frappe.whitelist() def reject_delivery_match(report_name, reason=None)`:
  - Flips status → `Rejected`; does not touch any invoice.
- `@frappe.whitelist() def rematch_delivery_report(report_name, invoice_name)`:
  - Overrides the suggested match; sets status back to `Suggested` for re-confirmation.

## Acceptance Criteria
- Confirm on an **unpaid** invoice with `payment_status=Paid` produces a submitted Payment Entry,
  invoice `outstanding_amount` drops to 0 (or by `amount_collected` for `Partial`), and the ledger
  balances.
- Confirm with `payment_status=Unpaid` stamps delivery data but posts **no** Payment Entry.
- Confirming an already-`Confirmed` report is a no-op (no double payment) — idempotent.
- Reject and re-match never leave partial writes on the invoice.
- `amount_collected` is validated against outstanding (do not over-allocate).

## Dependencies
- Todo 019, 020, 022
- Reuses `create_payment_entry` (Phase 0/existing code) — do not reimplement.

## Risks
- **Double payment** on re-confirm or race conditions — guard with the `payment_entry` link and
  a status check before posting.
- Partial delivery + partial payment interaction: decide whether `Partially Delivered` still
  allows full payment; document the chosen rule.
- Mode of payment for driver-collected cash must map to a valid Mode of Payment / account.

## Design rule: completion_status and payment_status are independent axes (2026-07-30)
Decided: a `Partially Delivered` order can still be fully `Paid`, and a `Full` delivery can still
be `Unpaid` (e.g. paid upfront regardless of what physically arrived, or invoiced on credit
regardless of delivery outcome). `confirm_delivery_match` keys mark-as-paid purely off
`payment_status`; `completion_status` only drives `custom_delivery_status`. No coupling between
the two.

## Implementation notes (2026-07-30)
Added three whitelisted endpoints to `klik_pos/api/delivery.py`:
- **`confirm_delivery_match(report_name, invoice_name=None, mark_paid=None)`** — stamps all six
  Todo 020 fields onto the target invoice, then (unless `payment_status` is `Unpaid` or
  `mark_paid=False`) calls the existing `create_payment_entry(invoice_doc, None, amount)` — `None`
  mode of payment lets it default to `Cash` + the company's default cash account, which is exactly
  what a driver-collected-cash delivery needs, so no new mode-of-payment mapping was needed.
  `amount` is `outstanding_amount` for `Paid`, or the human-confirmed `amount_collected` for
  `Partial` (validated: must be > 0 and cannot exceed `outstanding_amount` — the
  over-allocation guard this todo's acceptance criteria requires).
- **`reject_delivery_match(report_name, reason=None)`** — flips status only; deliberately leaves
  `matched_invoice`/`match_confidence` untouched for audit trail (what was suggested and rejected,
  and why) rather than nulling them. The optional `reason` is recorded as a timeline comment
  (`add_comment`) rather than overwriting `match_notes`, which explains the auto-match itself, not
  the human's rejection reason - two different pieces of information.
- **`rematch_delivery_report(report_name, invoice_name)`** — manual override, resets status to
  `Suggested` (not `Confirmed`) so it still requires a separate confirm call.
- **Double-payment guard**: two layers, since a single status check isn't safe under concurrent
  requests - (1) fast-path early return if already `Confirmed` (handles the common repeat-call
  case cheaply), (2) an immediate re-check of `reconciliation_status`/`payment_entry` right before
  calling `create_payment_entry`, so two near-simultaneous confirm calls that both passed check
  (1) can't both post a payment.
- Reject/re-match never touch the Sales Invoice at all, by construction (no invoice code path in
  either function) — trivially satisfies "never leave partial writes on the invoice."

### Bug found and fixed while testing: Todo 020's fields couldn't actually be written after submit
First end-to-end test of `confirm_delivery_match` against a real submitted invoice failed with
Frappe's own error: *"Not allowed to change Delivery Status after submission from Pending to
Delivered."* Todo 020's six `custom_delivery_*` fields were created `read_only: 1` but without
`allow_on_submit: 1` - and reconciliation, by definition, always runs *after* the invoice is
already submitted (delivery happens later than checkout). Fixed by:
- Adding `allow_on_submit: 1` to all six fields in both `klik_pos/klik_pos/custom/sales_invoice.json`
  and `ensure_delivery_reconciliation_fields()` in `setup/install.py`.
- Switching `ensure_delivery_reconciliation_fields()` from `create_custom_field` (creates once,
  silently skips if the Custom Field already exists) to `create_custom_fields(..., update=True)`
  wrapped around a single dict of all six fields - this upserts existing fields too, which is what
  let this exact fix apply to the already-patched `hd.phirun.me` site by simply re-running the
  function (patches themselves only execute once per site, tracked in Patch Log - re-running
  `bench migrate` would **not** have re-applied the fix without this change, since the patch
  already showed as executed).
- Manually invoked `ensure_delivery_reconciliation_fields()` once via `bench execute` for this
  site (since the existing patch entry wouldn't re-fire), confirmed via `bench console` that all
  six fields now show `allow_on_submit: 1`.

Verified end-to-end via a throwaway `bench execute`-run script (avoided `bench console`'s
heredoc/multi-line-`def` quirk noted earlier in this session) against five real submitted test
invoices, all cleaned up (cancelled + deleted) afterward:
- **Paid**: `confirm_delivery_match` posts a submitted Payment Entry, invoice `outstanding_amount`
  drops from 100 to 0.
- **Unpaid**: delivery fields stamped (`custom_delivery_status = Delivered`), no Payment Entry
  created, `outstanding_amount` unchanged.
- **Idempotent re-confirm**: second call on an already-`Confirmed` report returns the same
  `payment_entry` name as a no-op; exactly one `Payment Entry Reference` row exists for the
  invoice (no duplicate payment).
- **Partial without `amount_collected` set**: fails with a clear message, no Payment Entry.
- **Partial over-allocated** (`amount_collected` > `outstanding_amount`): fails with a clear
  message.
- **Partial with correct amount**: succeeds, `outstanding_amount` drops by exactly the confirmed
  amount (200 → 125 for a 75 collection).
- **Reject**: invoice's `custom_delivery_status` is provably unchanged before/after (`Pending` →
  `Pending`).
- **Re-match**: overrides the auto-matched invoice to a different one, status lands on
  `Suggested` (not `Confirmed`), confirming a re-match alone never finalizes anything.
