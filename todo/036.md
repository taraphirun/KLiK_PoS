# Todo 036: Cutover + Retire Legacy Stack

**Status:** 🔷 Phase A done (bot code fully decoupled from Postgres/MinIO, verified live against
hd.phirun.me) - Phase B (stopping the actual Postgres/Redis-as-DB/MinIO/ocr-service/NestJS/
frontend containers on the separate VM, 192.168.2.235) is the user's own next step, see notes.

## Description
Once capture (033), sync (034), media (035), and the KlikPOS-side Modules 10–13 are live, cut the
bot over to KlikPOS as the sole system of record and decommission the old services.

## Estimated Time
2-4 hours (plus a monitored parallel-run period)

## Steps
1. **Parallel run**: bot writes to SQLite + syncs to KlikPOS while the old Postgres path is kept
   read-only, until sync is proven reliable (e.g. N days, zero unexplained gaps).
2. **Data backfill**: migrate any historical Postgres deliveries/drivers still needed into Frappe
   (one-off script → Delivery Report / Driver), or archive them if not required.
3. **Reduce bot UI**: the bot's Next.js frontend is no longer the operational UI — either retire it
   or leave a minimal read-only status. Operational UI is now KlikPOS (Modules 11–13).
4. **Decommission**: stop and remove NestJS backend, Postgres, Redis/BullMQ, MinIO, and
   ocr-service from `docker-compose.yml`. Remove the unused Google Document AI / GenAI deps.

## Acceptance Criteria
- All new deliveries flow only through SQLite → KlikPOS; nothing depends on Postgres/NestJS.
- Historical data needed for reporting is present in Frappe (or explicitly archived).
- `docker-compose.yml` no longer starts the retired services; the bot + KlikPOS run the whole flow.
- A documented rollback exists until the parallel-run window closes.

## Dependencies
- Phases 9–12 (Modules 10–13) live; Todos 033–035 complete.

## Risks
- **Data loss on cutover** — do not decommission Postgres until backfill is verified and the
  parallel run is clean; keep backups.
- Reporting continuity — confirm KlikPOS reports/dashboards cover what the bot UI previously showed
  before retiring it.
- Hidden dependencies on MinIO URLs / NestJS endpoints elsewhere — grep and confirm before removal.

## Implementation notes (2026-08-03)

### Scope decided with the user, live in this pass
- Historical Postgres data: all test data, explicitly OK to discard rather than backfill ("all
  data at the moment are just testing. they all need to be clear before actual production").
- The old NestJS/Next.js dashboard: the user's stated need for it ("check the data from the bot
  local db, see if they sync properly") turned out to already be fully covered by the existing
  `/syncstatus` Telegram admin command (reports outbox Pending/Synced/Failed counts + recent
  failure details) - which the dashboard never actually showed anyway (it read Postgres, not the
  SQLite outbox). Confirmed OK to retire NestJS + frontend too, not just Postgres/Redis-as-DB/
  MinIO.
- Redis: kept, explicitly NOT retired this pass - still used for aiogram's own FSM state storage
  (RedisStorage) and photo-album batching, which is a real and current dependency, not legacy. The
  tradeoff (in-memory FSM would lose in-progress conversations on a bot restart) wasn't worth it to
  the user for this pass.
- ocr-service: confirmed unused in the bot's code already (no reference anywhere), always was safe
  to stop independent of everything else.

### What actually changed (bot repo: hd-delivery-telegram/delivery-bot)
`bot.py` had ~150 lines of real, load-bearing Postgres usage discovered mid-investigation - far
more than "a few dual-writes": the entire driver registration flow (start/register/approve/reject)
read/wrote a local `public."Driver"` table, `finalize_delivery` had a whole legacy dual-write
block (`delivery_bot.delivery_logs` + `public."Invoice"`, explicitly the thing this todo says to
delete), and config (bot token/reporting chat/timezone) came from a Postgres `SystemSetting`
table.

- **`local_store.py`**: new `driver_status` table (mirrors the existing `booklet_status`
  transition-detector pattern) - replaces the Postgres `public."Driver"` row's role of "remember
  the last status we acted on" for `driver_sync.py`'s poll loop.
- **`driver_sync.py`**: `poll_klikpos_status`/`_sync_one_driver_down` no longer take a `db_pool`
  param, use `local_store.get/set_driver_last_status` instead of Postgres. New
  `find_driver_by_telegram_id()` - a read-only KlikPOS lookup (reuses `list_drivers`, filters
  client-side - driver counts are low-volume, no new KlikPOS endpoint needed) used everywhere the
  bot needs to check "is this a known driver and what's their status" without that check itself
  registering anyone (unlike `sync_driver_from_bot`, which is create-or-update).
- **`bot.py`**: Postgres pool/schema, MinIO client, and every call site rewritten -
  registration/approval flow now reads/writes KlikPOS directly (via `driver_sync`); config
  (`DELIVERY_BOT_TOKEN`, new `ADMIN_TELEGRAM_IDS`/`REPORTING_CHAT_ID`/`REPORTING_TOPIC_ID`/
  `LOCAL_TZ`) is env-only; `upload_photos_to_minio`/`recover_pending_uploads` and the
  `finalize_delivery` legacy dual-write block deleted outright (dashboard being retired); the
  redundant `delivery_drafts` Postgres mirror of FSM state deleted (RedisStorage already persists
  this - confirmed by the bot's own startup log line, which predates this change).
- **`klik_pos/api/driver.py`** (klik_pos repo): `sync_driver_from_bot` gained a `phone_number`
  param, creation-only (same precedence as `driver_name`) - found during the rewrite that the
  bot's registration flow captures a phone number that had nowhere to go once the local Postgres
  `Driver.phoneNumber` column went away; this was the one real feature-parity gap, now closed.
- **`requirements.txt`**: `asyncpg`, `minio` removed.
- **`.env.example`** and the **live `.env`** (on the `hd` VM, `EnvironmentFile=` for
  `delivery-bot.service`): `DATABASE_URL`/`DB_SCHEMA`/`MINIO_*` removed; `ADMIN_TELEGRAM_IDS`/
  `REPORTING_CHAT_ID`/`REPORTING_TOPIC_ID`/`LOCAL_TZ` added - values read from the live Postgres
  `SystemSetting`/`User` tables one last time before rewriting `.env`, so behavior (which admin
  gets DMs, which group deliveries forward to) carries over exactly, not silently reset to blank.
