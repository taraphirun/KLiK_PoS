# Todo 046: Manual Delivery Confirm + No-Report Invoice Backfill

**Status:** ✅ Done

## Description
Two backend actions the daily reconciliation checklist needs (Module 17,
[phase-16.md](../phases/phase-16.md)): a manual "I know what happened, no bot report exists"
override for an invoice stuck Pending (Confirm Self-Pickup / Confirm Delivered when the driver
forgot to report), and a way to backfill an invoice for a page number that has *neither* an
invoice nor a Delivery Report at all (truly forgotten end-to-end) - ports the NestJS dashboard's
old `resolveMissing` endpoint.

## Files Changed
- `klik_pos/api/delivery.py`:
  - `_apply_payment_status_to_invoice_data` (new) - the Paid/Partial/Unpaid shaping logic
    extracted out of `create_invoice_from_delivery_report` so it's shared, not duplicated, with
    the new no-report path.
  - `set_manual_delivery_status(invoice_name, status)` - guarded against overriding an invoice
    that already has a Confirmed Delivery Report.
  - `create_invoice_for_unreported_page(page_number, invoice_data, ...)` - requires a customer up
    front (same rule as Module 15's Create Invoice modal), stamps `custom_invoice_ref`, no
    Delivery Report/confirm_delivery_match involved.
  - `create_invoice_from_delivery_report` also now stamps `custom_invoice_ref` from the report's
    `reported_invoice_no` (see bug note below) - a real fix, not new scope.

## Implementation notes (2026-08-02)

### Real bug found: backfilled invoices were invisible to invoice-ref lookups
First live test of the daily checklist showed an invoice created via
`create_invoice_from_delivery_report` and fully confirmed as `Delivered `- yet the checklist
reported it "Reported, No Invoice" (invoice missing) forever. Root cause: that function never
stamped `custom_invoice_ref` onto the created invoice - it only links via
`custom_delivery_report`/`matched_invoice`, so anything doing a `custom_invoice_ref`-keyed lookup
(the checklist's primary join) never found it. Fixed two ways: (1) `custom_invoice_ref` is now
defaulted from the report's `reported_invoice_no` when the caller doesn't set one explicitly, so
new backfills are always discoverable by ref; (2) defensively, `_classify_daily_checklist` (Todo
047) also falls back to a direct `matched_invoice` lookup for a Confirmed report even without a
ref match, so older pre-fix data doesn't misreport either.

### `set_manual_delivery_status`'s guard
Checks `invoice.custom_delivery_report` - if set and that report's `reconciliation_status` is
`Confirmed`, refuses the manual override and points at the normal reconciliation flow instead.
Deliberately a *lower-trust* path (no GPS/photo/driver identity), so it must never be able to
silently clobber a bot-verified outcome.

### Live verification (bench console against hd.phirun.me)
Exercised both new endpoints plus the refactored `create_invoice_from_delivery_report` (regression
check) together: missing-customer rejection, successful no-report backfill with `custom_invoice_ref`
correctly stamped, duplicate-ref rejection, manual Self-Pickup confirm, invalid-status rejection,
and the Confirmed-report override guard (correctly blocked). A few $1 test invoices against the
demo customer couldn't be cleanly cancelled afterward due to this site's currently very tight AZT
stock (Allow Negative Stock is intentionally off per the user's own earlier decision) - left in
place rather than touch Stock Settings; flagged to the user to remove manually.
