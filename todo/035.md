# Todo 035: Media Buffering + Upload to Frappe File

**Status:** ✅ Done (capture, upload, and attach all verified; no KlikPOS-side UI to *view* the
attached media exists yet — see notes)

## Description
Buffer delivery photos and voice notes locally at capture time and upload them to Frappe File on
sync, replacing MinIO. Attach the uploaded files to the corresponding Delivery Report.

## Estimated Time
2-3 hours

## Files to Change
- Bot side (`hd-delivery-telegram/delivery-bot`): download Telegram media to local disk at capture;
  upload during sync.
- KlikPOS side (`klik_pos/api/delivery.py`): accept file uploads and attach to a Delivery Report
  (or reuse Frappe's standard file-upload + `attach` linkage).

## Behaviour
- At capture: fetch the Telegram file(s) to a local media dir; store paths in the SQLite row
  (Todo 033).
- At sync: upload each file to Frappe (Frappe File, private), link it to the Delivery Report's
  `photos` / `voice_note` fields, then it may be pruned locally after successful attach.
- Order: upload media first, then submit/patch the Delivery Report so links resolve.

## Acceptance Criteria
- Photos/voice captured offline are stored locally and survive a restart.
- On sync, media lands in Frappe File, attached to the right Delivery Report, viewable from the
  deliveries UI (Todo 029).
- Re-sync does not create duplicate file attachments (idempotent per `bot_delivery_id` + file).

## Dependencies
- Todo 033, 034; Phase 9 Todo 019 (photo/voice fields). ~~Todo 029 (viewing media)~~ — Module 12
  (and Todo 029 with it) was dropped 2026-07-31 (see phases/phase-11.md); no replacement media
  viewer was built as part of this todo either (see Known gap below).

## Risks
- Large media over poor connectivity — compress/limit resolution; upload with resumable/retry.
- Private vs public files — delivery photos should be private Frappe files with proper permissions.
- Local disk growth — prune only after confirmed successful attach.

## Implementation notes (2026-07-31, in both repos)

### `upload_delivery_file` (klik_pos/api/delivery.py, this repo) - not Frappe's stock upload
Frappe's built-in `/api/method/upload_file` rejects any file type outside a hardcoded allowlist
(`frappe.handler.ALLOWED_MIMETYPES` - JPG/PNG/GIF/PDF/text/office docs/mp4, **no audio formats at
all**) for any user without Desk access. The bot's service account deliberately has no Desk access
(least privilege - see Todo 034's notes), so voice notes (`audio/ogg`) would always be rejected
through that endpoint. Rather than grant Desk access just to clear one MIME check, added a
dedicated endpoint that calls `frappe.utils.file_manager.save_file()` directly - the actual file-
saving primitive Frappe's own `upload_file` handler eventually calls, which has no such
restriction itself (the MIME check is an extra HTTP-handler-level guard, not something
`save_file()` enforces). Requires `report_name` (the Delivery Report must already exist) so the
file gets proper doctype-linked permission scoping via `attached_to_doctype`/`attached_to_name` -
not an orphaned, owner-only file.

**Deviation from the spec's stated order**: "upload media first, then submit/patch the Delivery
Report" (this todo's Behaviour section) - implemented as the reverse (submit first, then upload)
because doctype-linked file permissions need the docname to exist first; there's no doctype/
docname to attach to before the report is created. Documented here since it's a real, deliberate
deviation from the written spec, not an oversight.

### `attach_delivery_media` (klik_pos/api/delivery.py) - records URLs onto the report
Merges `photo_urls` into the existing `photos` JSON array (idempotent - a URL already present is
not duplicated) and sets `voice_note` (single Attach field, overwrites). Found and fixed a Frappe
gotcha while building this: assigning a raw Python `list` to a JSON-fieldtype field throws "Value
for Photos cannot be a list" - only a `dict` auto-serializes on assignment, a `list` must be
`json.dumps()`'d by the caller first. This was *also* a latent bug in the original
`submit_delivery_report` (Todo 021) that had never been exercised with a real `photos` list until
now - fixed in the same pass (see this repo's own commit).

### Bot side (`hd-delivery-telegram/delivery-bot`)
`sync_worker.py`'s `_upload_and_attach()`/`_upload_one()` call `upload_delivery_file` (not
`upload_file`) for each local photo/voice path, collect the returned `file_url`s, then call
`attach_delivery_media` once with all of them. Local files are pruned **only** after a confirmed
successful `attach_delivery_media` call, per this todo's risk note - a media upload succeeding but
the attach call failing (transient network blip) leaves the local file in place for the next sync
pass to retry, rather than silently losing it.

### Known gap: no KlikPOS-side media viewer
This todo covers capture → upload → attach; it does not include a UI to actually *view* the
attached photos/voice notes from KlikPOS (`DeliveryReconciliationPage.tsx`, Todo 024, does not
currently render `photos`/`voice_note`). The original spec's "viewable from the deliveries UI"
criterion pointed at Todo 029, which no longer exists (Module 12 dropped). Files are correctly
stored as private Frappe Files attached to the Delivery Report, so they're reachable via the
Desk UI's file list on that document right now - a dedicated reconciliation-page viewer is a
reasonable, separate follow-up if wanted.

### Verification (full trace, covers Todo 034 + 035 together)
Live end-to-end run against the real KlikPOS site: inserted a SQLite outbox row with 2 photo paths
+ 1 voice path → `sync_worker.run_once()` → `submit_delivery_report` created a real Delivery
Report → both photos and the voice note uploaded via `upload_delivery_file` and attached via
`attach_delivery_media` → confirmed on the actual document (`photos` JSON array had both file
URLs, `voice_note` had the third) → all three local files pruned only after that confirmed
success. Two real bugs surfaced and were fixed during this exact test:
1. MySQL's `DATETIME` column rejected Python's default `isoformat()` output (microseconds + a
   `+00:00` offset suffix) even though `get_datetime()` parses that string fine on its own - the
   failure happens one layer down at the DB driver. Fixed on the bot side
   (`sync_worker._to_klikpos_datetime`) by normalizing to plain `YYYY-MM-DD HH:MM:SS` before
   sending, matching the format used everywhere else in this integration.
2. The MIME-allowlist issue described above (initially misdiagnosed as a mysterious HTTP 417 -
   the real cause was only visible in the response body, not the status code).
Also verified: a permanent-failure payload (deliberately invalid `completion_status`) reached
KlikPOS, got validated and rejected, and the row was marked `Failed` after exactly one attempt
rather than retried. All test data (Delivery Reports, attached Files) cleaned up after each run.
