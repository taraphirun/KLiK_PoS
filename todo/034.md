# Todo 034: Sync Worker (Store-and-Forward)

**Status:** ✅ Done

## Description
A background loop in the bot that forwards `Not Synced` SQLite rows to KlikPOS and records the
result — the drain half of the offline-first design.

## Estimated Time
2-3 hours

## Files to Change (in `hd-delivery-telegram/delivery-bot`)
- `bot.py` / new `sync_worker.py` (MODIFY/New)

## Behaviour
- Periodically (and on reconnect) select rows where `sync_status != Synced`.
- For each: upload media (Todo 035), then POST to KlikPOS `submit_delivery_report` (Todo 021) with
  `bot_delivery_id` as the idempotency key.
- On HTTP 2xx: set `sync_status = Synced`, store `synced_delivery_report`.
- On failure: increment `sync_attempts`, record `last_sync_error`, keep `Not Synced` (or `Failed`
  after N attempts), and back off exponentially.
- Health/status command so a driver/admin can see pending vs synced counts.

## Acceptance Criteria
- With KlikPOS down, rows stay `Not Synced` and the worker retries without crashing.
- When KlikPOS returns, all pending rows sync and flip to `Synced` exactly once (no duplicates in
  Frappe — verified by the Todo 021 idempotency on `bot_delivery_id`).
- Transient errors (timeouts, 5xx) retry; permanent errors (validation 4xx) mark `Failed` and are
  surfaced, not retried forever.

## Dependencies
- Todo 033 (SQLite store), Todo 035 (media upload), Phase 9 Todo 021 (ingestion API)

## Risks
- Double-send races — rely on server idempotency, and mark `Synced` only after a confirmed 2xx.
- Clock/timezone: send the captured `timestamp`, not send-time (deliveries may sync much later).
- Auth token rotation — worker must refresh/handle expired API keys gracefully.

## Implementation notes (2026-07-31, in `hd-delivery-telegram`)

### Dedicated KlikPOS API user (klik_pos side, this repo)
Created `delivery-bot@hd-telegram.local` (System User, role "Delivery Bot", no elevated
permissions) with an API key/secret, since `submit_delivery_report`/`sync_driver_from_bot` already
write with `ignore_permissions=True` internally (Todo 021/026) - the account just needs to be a
valid authenticated non-guest session. Credentials live in `delivery-bot/.env`
(`KLIKPOS_BASE_URL`/`KLIKPOS_API_KEY`/`KLIKPOS_API_SECRET`) - see that repo's own commit for why
`.env` needed to stop being tracked in git first (real secrets were already committed there for
Postgres/Telegram/MinIO, unrelated to this work but fixed alongside it).

One extra grant was needed beyond the base role: `upload_delivery_file`
(`klik_pos/api/delivery.py`, Todo 035) needs the calling user to have real `create`/`write`
permission on `Delivery Report` (not just `ignore_permissions=True` inside the endpoint) because
it calls `frappe.utils.file_manager.save_file()`, which itself doesn't check permissions, but
`attach_delivery_media`'s follow-up `report.save()` does when called on a doc the user doesn't
already have write access to via the doctype's own permission table. Granted via a `Custom DocPerm`
row for the `Delivery Bot` role (read/write/create on `Delivery Report`, permlevel 0) rather than
widening `ignore_permissions` further.

### `delivery-bot/sync_worker.py` (new)
`run_forever()` loops on `SYNC_INTERVAL_SECONDS` (default 15s), each pass calling `run_once()`:
fetch up to `SYNC_BATCH_SIZE` Not-Synced rows, filter to ones actually due for retry (see backoff
below), then `sync_one()` per row - `submit_delivery_report` → on success, upload local media
files and attach them → `mark_synced`.

**Error classification** (Acceptance Criteria: transient retries, permanent surfaces and stops):
- Network/timeout exceptions, or HTTP 5xx from KlikPOS itself → transient → stays `Not Synced`,
  *unless* `sync_attempts` has already hit `SYNC_MAX_ATTEMPTS` (default 15), at which point it's
  flipped to `Failed` too - a row that's failed to even reach the server 15 times in a row is
  probably not a transient blip (wrong URL, revoked key, DNS issue), so it stops silently
  hammering and surfaces for a human to look at instead.
- HTTP 200 with `{"success": false, ...}` in the body → **always** permanent, regardless of
  attempt count. This is deliberate: Frappe whitelisted methods (including
  `submit_delivery_report`) return validation failures as HTTP 200 with a `success` flag, not an
  HTTP 4xx - retrying the *identical* payload against the *identical* validation rule will never
  succeed, so there's no reason to wait for the attempt cap.
- Backoff (`_due_for_retry`): simple exponential-ish wait computed from `sync_attempts` and the
  row's `updated_at` at read time (`SYNC_INTERVAL_SECONDS * 2^attempts`, capped at 5 minutes) -
  no separate scheduler/stored next-retry-time, just a filter applied each pass.

### `/syncstatus` admin command (bot.py)
Admin-only (checked against `admin_telegram_ids`, same set used for registration-approval DMs).
Shows pending/synced/failed counts plus the 5 most recent failures with their `last_sync_error`,
satisfying this todo's "health/status command" requirement. Resetting a `Failed` row back to
`Not Synced` for a retry currently requires a direct SQLite edit - no admin command for that yet
(acceptable for a first pass; `Failed` rows are meant to need human judgment about *why* before
blindly retrying anyway).

### Verification
Full round trip verified against the real KlikPOS site (`bench execute`-driven manual runs, not
an automated test suite): SQLite insert → `sync_worker.run_once()` → real `Delivery Report`
created with GPS/driver/status fields correctly mapped; duplicate-submission idempotency; the
permanent-failure path (deliberately invalid `completion_status` → `Failed` after exactly 1
attempt, confirmed excluded from the next `fetch_pending()` call). See Todo 035's notes for the
media-attach half of the same test. Two real bugs found and fixed during this verification (both
KlikPOS-side format/permission issues, not sync-worker logic bugs) - detailed in Todo 035's notes
since that's where they surfaced.
