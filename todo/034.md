# Todo 034: Sync Worker (Store-and-Forward)

**Status:** ⬜ Not started

## Description
A background loop in the bot that forwards `Not Synced` SQLite rows to KlikPOS and records the
result — the drain half of the offline-first design.

## Estimated Time
2-3 hours

## Files to Change (in `hd-delivery-telegram/delivery-bot`)
- `bot.py` / new `sync_worker.py` (MODIFY/New)

## Behaviour
- Periodically (and on reconnect) select rows where `sync_status != Synced`.
- For each: upload media (Todo 035), then POST to KlikPOS `submit_delivery_report` (Todo 021) with
  `bot_delivery_id` as the idempotency key.
- On HTTP 2xx: set `sync_status = Synced`, store `synced_delivery_report`.
- On failure: increment `sync_attempts`, record `last_sync_error`, keep `Not Synced` (or `Failed`
  after N attempts), and back off exponentially.
- Health/status command so a driver/admin can see pending vs synced counts.

## Acceptance Criteria
- With KlikPOS down, rows stay `Not Synced` and the worker retries without crashing.
- When KlikPOS returns, all pending rows sync and flip to `Synced` exactly once (no duplicates in
  Frappe — verified by the Todo 021 idempotency on `bot_delivery_id`).
- Transient errors (timeouts, 5xx) retry; permanent errors (validation 4xx) mark `Failed` and are
  surfaced, not retried forever.

## Dependencies
- Todo 033 (SQLite store), Todo 035 (media upload), Phase 9 Todo 021 (ingestion API)

## Risks
- Double-send races — rely on server idempotency, and mark `Synced` only after a confirmed 2xx.
- Clock/timezone: send the captured `timestamp`, not send-time (deliveries may sync much later).
- Auth token rotation — worker must refresh/handle expired API keys gracefully.
