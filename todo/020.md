# Todo 020: Sales Invoice Custom Fields for Reconciled Delivery Data

**Status:** ✅ Done

## Description
Add custom fields to the Sales Invoice doctype that hold the **reconciled** (trusted) delivery
outcome. These are written only after a Delivery Report is confirmed against the invoice
(Todo 023) — never directly by the bot. This is what reports, the POS UI, and the delivery bot
query to know an invoice's delivery state.

## Estimated Time
30-60 minutes

## Files to Change
- `klik_pos/klik_pos/custom/sales_invoice.json` (MODIFY — add custom fields)
- `klik_pos/install.py` or the setup/install module (ensure fields registered on install)

## Fields to Add (on Sales Invoice)
- `custom_delivery_status` (Select: Pending / Delivered / Partially Delivered / Not Delivered) — default Pending
- `custom_delivery_driver` (Data — free text, mirrors the Delivery Report driver field)
- `custom_delivered_at` (Datetime)
- `custom_delivery_gps_latitude` (Float), `custom_delivery_gps_longitude` (Float)
- `custom_delivery_report` (Link → Delivery Report) — the confirmed source record

## Design Note: fully denormalized (incl. GPS) — decided
All delivery fields are copied onto the Sales Invoice at confirm-time (Todo 023), not read
through the `custom_delivery_report` link. Rationale:
- Reporting is done by switching the report's document type to Sales Invoice, which requires
  delivery fields to be real columns on the invoice (Frappe Report Builder / list filters cannot
  traverse a Link to child fields).
- GPS is denormalized intentionally to support a planned **live delivery dashboard** and any
  invoice-centric view that plots drop location, and to freeze a snapshot of where each invoice
  was delivered.
- Trade-off accepted: the live dashboard may instead render off the `Delivery Report` doctype,
  in which case GPS is available there natively and the invoice copy is redundant *for that
  dashboard* — but it is retained as insurance for invoice-side views and snapshot completeness.
- The `custom_delivery_report` link is still kept for audit/drill-down (raw payload, notes).

## Acceptance Criteria
- Fields appear on the Sales Invoice after install/migrate and are queryable via the API.
- `custom_delivery_status` defaults to `Pending` for new invoices.
- Fields are read-only in the standard desk form (they are system-maintained by reconciliation).
- Existing invoice creation/list APIs (`get_sales_invoices`) can optionally return the new
  fields without breaking current consumers.

## Dependencies
- Todo 019 (for the `custom_delivery_report` link target)

## Risks
- Field name collisions with existing `custom_delivery_*` fields (there is already
  `custom_delivery_date`, `custom_delivery_personnel`) — verify names before adding.
- Adding required/defaulted fields must not break the existing POS invoice creation path.

## Implementation notes (2026-07-30)
Checked first: `custom_delivery_personnel`/`custom_delivery_personnel_name` already exist (an
internally-assigned delivery person, unrelated to bot reconciliation) — no name collision with the
new fields since they serve a different purpose. Also discovered `custom_delivery_date` is
referenced in `klik_pos/api/sales_invoice.py` (lines ~1913, 2043, 3749, 3996,
`doc.custom_delivery_date = ...`) but **does not exist** as either a DB column or a Custom Field —
it's a pre-existing latent bug (assigning an undefined attribute on a Document silently does
nothing on save). Out of scope for this todo; not fixed, just noting it here since it's exactly
the kind of collision this todo's Risks section asked to check for.

Added 6 new fields to the existing "Delivery" section on Sales Invoice (right after
`custom_delivery_personnel_name`, alongside the pre-existing delivery-personnel fields):
`custom_delivery_status` (Select, default Pending), `custom_delivery_driver` (Data — the
bot-reported driver name, distinct from `custom_delivery_personnel`), `custom_delivered_at`
(Datetime), `custom_delivery_gps_latitude`/`custom_delivery_gps_longitude` (Float, precision 6),
`custom_delivery_report` (Link → Delivery Report). All read-only per the acceptance criteria
(system-maintained by reconciliation, Todo 023).

Followed the established pattern from Phase 8 (`ensure_pos_print_format_field`):
`ensure_delivery_reconciliation_fields()` in `klik_pos/setup/install.py` (called from
`after_install()` for fresh installs, using `create_custom_field` per-field guarded by an
existence check), plus `klik_pos/patches/v16_0/add_delivery_reconciliation_fields.py` registered in
`patches.txt` under `[post_model_sync]` for this and future existing sites (runs after Delivery
Report's own DocType sync, so the Link target exists in time).

Hit and fixed a path mistake while wiring the patch: initially created the patch file under the
double-nested `klik_pos/klik_pos/klik_pos/patches/v16_0/` (mirroring the Phase 8 utils.py mistake)
instead of the correct single-nested `klik_pos/klik_pos/patches/v16_0/` — caught immediately via
`ModuleNotFoundError` on `bench migrate`, moved the file, cleaned up the empty stray directories.

For `klik_pos/klik_pos/custom/sales_invoice.json`: tried `bench export-fixtures` first (no-op —
that hook only exports Property Setters, not Custom Fields) then
`frappe.modules.utils.export_customizations()` (the real underlying function), but that does a
full re-export of every Custom Field on the doctype, reordering everything alphabetically and
pulling in unrelated schema-drift columns from the current Frappe version (`allow_bulk_edit`,
`mask`, `set_only_once`) plus splitting Sales Invoice Item's fields into a new sibling file —
all noise unrelated to this change. Reverted that and hand-added the 6 new fields directly, in the
same sparse/minimal dict format already used by the file's existing `custom_ds_roofing_spec`/
`custom_description` entries, keeping the diff to just the new fields.

Verified via `bench --site hd.phirun.me migrate` (clean, both from the patch path and re-running
against the updated fixture) and `bench console`:
- All 6 fields exist as real Sales Invoice DB columns.
- `custom_delivery_status` defaults to `Pending` — confirmed on a real newly-inserted Sales
  Invoice, not just the field metadata.
- All 6 fields are read-only per the Sales Invoice meta.
- Normal invoice insert/delete still works unaffected; test invoice cleaned up after verification.

## Correction (2026-07-30, found during Todo 023)
Original fields were `read_only: 1` with no `allow_on_submit`, which meant Frappe's own
submitted-document immutability check blocked writing them - discovered when Todo 023's
`confirm_delivery_match` tried to stamp them onto a real submitted invoice and got *"Not allowed
to change Delivery Status after submission."* Since reconciliation always runs after the invoice
is already submitted, this made the fields unusable for their entire purpose. Fixed by adding
`allow_on_submit: 1` to all six fields (fixture + `setup/install.py`) and switching
`ensure_delivery_reconciliation_fields()` to `create_custom_fields(..., update=True)` so it can
correct already-existing sites, not just fresh installs. Full detail in [Todo 023](023.md).
