# Todo 054: Lock Actions on Closed Days + Scheduled (Later) Delivery Dates

**Status:** ✅ Done

## Description
Two follow-ups to Daily Reconciliation, requested by the user 2026-08-03:

1. Every manual action button on the checklist should disappear once the day is Closed, and
   reappear the moment it's Reopened. Previously the buttons stayed live even after closing.
2. A new acceptable resolution for a booklet page: **Set Delivery Date**, for invoices purchased
   today but asked to be delivered on a later date (pre-orders). Setting the date resolves the
   page on its own posting date, but the invoice must re-surface - actionable - on the target
   date's own checklist, using the same booklet-group card UI, so it isn't just noted and
   forgotten.

## Bug found while wiring this up
`postJson`'s existing behavior (`throw` whenever `result.message.success === false`) meant
`closeDailyReconciliation`'s caller never actually saw `res.success === false` - the `if
(!res.success)` branch in `handleClose` (including the old regex-based blocking-number
extraction from Todo 047/052) was dead code; the "still need action" banner never rendered in
practice. Fixed by adding `postJsonExpectResult`, which returns the body instead of throwing on a
business-logic failure (still throws on a real transport failure), and switching
`closeDailyReconciliation` to use it. This is a **pre-existing bug from Todo 047**, not introduced
this round - flagging in case the same dead-code pattern (`if (!result.success) throw ...` right
after a `postJson` call) matters elsewhere; every other call site still works correctly because
they only cared about the thrown error's message text, never the structured fields.

## Design notes

### Scheduled is closable on its own date, actionable on the target date
`_classify_number` returns `"Scheduled"` for the *booklet page's own date* (closable, added to
`CLOSABLE_STATUSES`) - the paper page itself is genuinely accounted for once staff commit to a
delivery date. Separately, `_get_scheduled_deliveries(target_date)` surfaces the *same invoice*
again on the *requested* date, with its real live status (Pending Fulfillment / Delivered /
Partially Delivered / Self Pickup) - this is what actually blocks that date's Close Day if not yet
resolved. The two queries are independent (one keyed by `posting_date`, one by
`custom_requested_delivery_date`), so an invoice legitimately appears in two different date's
checklists at once - by design, not a duplicate-counting bug.

### Validation: target date must be after posting date
`set_requested_delivery_date` throws if the target date isn't after the invoice's own
`posting_date` - without this, someone could set today's date as the "requested delivery date"
and trivially mark a page Scheduled/closable without ever confirming a real delivery outcome,
defeating the whole point of the gate.

### Decisions made with the user, 2026-08-03 (via AskUserQuestion)
- Target-date behavior: **actionable, blocks close** (not just a reminder) - confirmed by
  live-testing that closing the target date is genuinely blocked until Confirm Delivered/
  Self-Pickup.
- Scope of "Set Delivery Date": **booklet page rows only** (Pending Fulfillment), not offered on
  "Invoices without a physical reference" - those are a separate, already-informational-only
  concern (Todo 050).
- Editability: **editable/clearable anytime before delivered** - `set_requested_delivery_date` can
  be called again to reschedule; `clear_requested_delivery_date` fully undoes it. Both gated to
  Pending/Not Delivered only, same spirit as `unlink_invoice_page`.

### readOnly scope: Closed only, not Needs Re-review
`isReadOnly = closing?.status === "Closed"` deliberately excludes "Needs Re-review" - that status
exists specifically so staff can address whatever drifted since closing, and hiding the actions
would make that impossible without first invoking the System-Manager-only Reopen. Reopened simply
isn't Closed, so it's already read-write without special-casing.

  drift-to-`Needs Re-review` result. All test data cleaned up, no leftovers.

## Addendum (2026-08-03, same-day follow-up): Scheduled blocks the booklet, not the day
User question after the first pass shipped: "does a Scheduled invoice still block that booklet
from closing?" It didn't - `CLOSABLE_STATUSES` was shared by both `close_daily_reconciliation` and
`close_booklet`, so Scheduled was closable for both. Confirmed with the user this should differ:
closing a *day* is fine with "the delivery is scheduled and tracked" (the real outcome gets caught
on the target date's own checklist later); closing a *booklet* retires it permanently, so a page
whose real outcome is still unknown shouldn't be enough to sign off on.

Split into two constants in `klik_pos/api/booklet.py`:
- `CLOSABLE_STATUSES` (unchanged) - used by `close_daily_reconciliation`, includes Scheduled.
- `BOOKLET_CLOSABLE_STATUSES = CLOSABLE_STATUSES - {"Scheduled"}` (new) - used by `close_booklet`'s
  blocking check only.

Live-verified: a booklet page set to Scheduled lets that *day* close successfully, but blocks
`close_booklet` for that booklet with the page number listed, exactly as `Void`/`Delivered`/etc.
already did for other unresolved statuses. No frontend changes needed - `get_booklet_status`'s
response shape is unchanged, the Booklets page already renders whatever status comes back.
