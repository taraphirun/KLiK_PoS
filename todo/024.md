# Todo 024: Frontend Reconciliation Page

**Status:** ✅ Done (backend-verified; not yet visually checked in a live browser — no browser tool available this session)

## Description
A page in the POS SPA where staff review incoming delivery reports and reconcile them. Shows a
queue of Delivery Reports (Unmatched / Suggested), the suggested invoice and why it matched, and
lets the user confirm, reject, re-match, and toggle mark-as-paid.

## Estimated Time
3-4 hours

## Files to Change
- `klik_spa/src/pages/DeliveryReconciliationPage.tsx` (New)
- `klik_spa/src/services/delivery.ts` (New — API client for Todo 021/023 endpoints)
- `klik_spa/src/types/index.ts` or `klik_spa/types/index.ts` (MODIFY — `DeliveryReport` interface)
- Routing + navigation entry (wherever POS routes/menus are registered)

## UI Requirements
- List/queue of delivery reports filtered by `reconciliation_status`, newest first.
- Per report: driver, timestamp, GPS (link to map), delivery status, amount collected,
  paid-at-location flag, reported invoice no.
- Suggested invoice card with `match_confidence` and the matched signals; button to open the
  full invoice.
- Actions: **Confirm match**, **Reject**, **Re-match** (search/pick a different invoice),
  and a **Mark as paid** toggle (defaulted from `paid_at_location`).
- Optimistic feedback + toast on success/failure; refresh the queue after an action.
- Badge/count of pending reports for the nav (so staff see the backlog).

## Acceptance Criteria
- Confirming a match updates the invoice and (if applicable) posts payment, then removes the
  report from the pending queue.
- Re-match lets the user search invoices and reassign before confirming.
- Low-confidence / unmatched reports are visually distinct and sortable to the top.
- `npm run build` passes with no TypeScript errors.

## Dependencies
- Todo 021 (ingestion), 022 (match), 023 (reconciliation endpoints)

## Risks
- Invoice search for re-match must scope to the right POS profile/company to avoid cross-tenant
  mismatches.
- Keep the collected-amount editable but validated against outstanding, mirroring Todo 023.

## Implementation notes (2026-07-30)

### Backend addition
Todo 021/023 never added a *list* endpoint - added `get_delivery_reports(status=None, search="",
start=0, limit=100)` to `klik_pos/api/delivery.py`. Defaults to the actionable queue
(`Unmatched,Suggested`); pass `status="Confirmed,Rejected"` for history. Verified via
`bench execute` (default queue, history, search-by-driver all correct).

Also extended `confirm_delivery_match` with an `amount_collected` parameter so the UI can supply
the human-confirmed Partial-payment amount in the same call that confirms, instead of a separate
write beforehand (avoided using the generic `frappe.client.set_value` RPC from the frontend, which
would've worked but doesn't fit this app's pattern of dedicated endpoints). Verified end-to-end via
`bench execute`: submits a Partial delivery, confirms with `amount_collected=90` in one call,
invoice `outstanding_amount` drops correctly, and the amount persists on the Delivery Report.

### Frontend
- `klik_spa/src/services/delivery.ts` (new) - typed client for `get_delivery_reports`,
  `confirm_delivery_match`, `reject_delivery_match`, `rematch_delivery_report`. `DeliveryReport`
  interface lives here (like `OutstandingSalesInvoice` in `paymentEntry.ts`), not in the shared
  `types/index.ts`, matching that existing precedent.
- `klik_spa/src/pages/DeliveryReconciliationPage.tsx` (new) - Pending Queue / History tabs (mirrors
  `PaymentEntriesPage.tsx`'s tab pattern), search, and a card per report showing driver, GPS map
  link, reported invoice no, the suggested/matched invoice with confidence badge and match notes,
  amount-collected input (Partial only), mark-as-paid toggle, and Confirm / Reject / Re-match
  actions. Re-match opens an inline invoice picker reusing the existing
  `getOutstandingSalesInvoices` search (already company-scoped via `get_current_pos_profile()` -
  satisfies this todo's cross-tenant risk note with no new endpoint).
- Routed at `/deliveries/reconcile` (`router/index.tsx`).
- Nav: added to both `RetailSidebar.tsx` (desktop) and `BottomNavigation.tsx` (mobile), gated
  behind the same `is_admin_user` flag as the existing Dashboard link (Delivery Report's only
  DocType permission is System Manager, so a non-admin nav entry would just 403). Also fixed both
  navs' disabled-tooltip text, which was hardcoded to "Sales Dashboard..." regardless of which
  gated item was disabled - now interpolates the actual item label, since reusing that gate for a
  second item made the pre-existing hardcoding visibly wrong.
- Added a pending-count badge on the sidebar icon (polls `get_delivery_reports()`'s default-queue
  `total_count` every 60s) - the explicit "badge/count of pending reports for the nav" UI
  requirement.

### Known limitation (documented, not fixed here)
Re-match's invoice search reuses `get_outstanding_sales_invoices`, which only returns invoices
with `outstanding_amount > 0`. An already-fully-paid invoice (e.g. paid by bank transfer ahead of
delivery) won't appear in the re-match picker. Acceptable for v1 since most delivery-reconciliation
targets are exactly the unpaid/partial credit sales this module exists for (Module 6); building a
separate unrestricted invoice-search endpoint was out of scope for this pass.
