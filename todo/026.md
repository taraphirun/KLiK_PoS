# Todo 026: Driver Management API + Bot Sync Bridge

**Status:** ⬜ Not started

## Description
Endpoints to manage drivers from KlikPOS (create / approve / reject / suspend) and a sync bridge
that keeps the Frappe `Driver` master and the delivery bot's Postgres `Driver` table consistent.

## Estimated Time
2-3 hours

## Files to Change
- `klik_pos/api/driver.py` (New)

## Endpoints
- `@frappe.whitelist() def list_drivers(status=None, search=None)` — paginated list for the UI.
- `@frappe.whitelist() def upsert_driver(data)` — create/update a driver (name, phone, telegram
  fields, status).
- `@frappe.whitelist() def set_driver_status(driver, status)` — approve (`Active`), `Rejected`,
  or suspend.
- `@frappe.whitelist() def sync_driver_from_bot(payload)` — the bot calls this when a driver first
  messages it: match on `bot_driver_id` or `telegram_user_id`, attach `telegram_user_id` /
  `chat_id` / `telegram_username` to the Frappe record (create as `Pending` if unknown).

## Sync direction (Frappe is master — decided)
- KlikPOS → bot: on approve/reject, notify the bot (webhook or the bot polls) so it honors the
  new status before messaging a driver.
- bot → KlikPOS: `sync_driver_from_bot` backfills Telegram identity onto the Frappe record.
- Precedence: Frappe wins on `status` and profile fields; the bot wins only on Telegram-identity
  fields (`telegram_user_id`, `telegram_username`, `chat_id`).

## Acceptance Criteria
- Creating a driver in KlikPOS produces a `Driver` record and (if wired) is retrievable by the bot.
- `sync_driver_from_bot` is idempotent: same `telegram_user_id` updates rather than duplicates.
- Approve/reject flips `status` and is reflected on the next bot interaction.
- All endpoints are authenticated; the bot uses a scoped API key/service user (as in Todo 021).

## Dependencies
- Todo 025 (Driver DocType)
- Coordinates with the bot repo (`hd-delivery-telegram`) — bot-side changes are out of scope for
  this repo but the contract (payload shape) must be documented here.

## Risks
- Two-way sync can loop or conflict; define a clear precedence (Frappe status wins;
  bot Telegram identity wins) and never overwrite the other side's owned fields.
- Network/availability: bot and Frappe may be up independently — make sync retry-safe, not
  fire-and-forget.
