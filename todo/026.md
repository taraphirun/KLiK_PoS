# Todo 026: Delivery Driver Management API + Bot Sync Bridge

**Status:** ✅ Done (KlikPOS-side endpoints backend-verified; bot-side wiring not started, same
caveat as [TASK-001](../bugs.md))

## Description
Endpoints to manage drivers from KlikPOS (create / approve / reject / suspend) and a sync bridge
that keeps the Frappe `Delivery Driver` master and the delivery bot's Postgres `Driver` table consistent.

## Estimated Time
2-3 hours

## Files to Change
- `klik_pos/api/driver.py` (New)

## Endpoints
- `@frappe.whitelist() def list_drivers(status=None, search=None)` — paginated list for the UI.
- `@frappe.whitelist() def upsert_driver(data)` — create/update a driver (name, phone, telegram
  fields, status).
- `@frappe.whitelist() def set_driver_status(driver, status)` — approve (`Active`), `Rejected`,
  or suspend.
- `@frappe.whitelist() def sync_driver_from_bot(payload)` — the bot calls this when a driver first
  messages it: match on `bot_driver_id` or `telegram_user_id`, attach `telegram_user_id` /
  `chat_id` / `telegram_username` to the Frappe record (create as `Pending` if unknown).

## Sync direction (Frappe is master — decided)
- KlikPOS → bot: on approve/reject, notify the bot (webhook or the bot polls) so it honors the
  new status before messaging a driver.
- bot → KlikPOS: `sync_driver_from_bot` backfills Telegram identity onto the Frappe record.
- Precedence: Frappe wins on `status` and profile fields; the bot wins only on Telegram-identity
  fields (`telegram_user_id`, `telegram_username`, `chat_id`).

## Acceptance Criteria
- Creating a driver in KlikPOS produces a `Delivery Driver` record and (if wired) is retrievable by the bot.
- `sync_driver_from_bot` is idempotent: same `telegram_user_id` updates rather than duplicates.
- Approve/reject flips `status` and is reflected on the next bot interaction.
- All endpoints are authenticated; the bot uses a scoped API key/service user (as in Todo 021).

## Dependencies
- Todo 025 (Delivery Driver DocType)
- Coordinates with the bot repo (`hd-delivery-telegram`) — bot-side changes are out of scope for
  this repo but the contract (payload shape) must be documented here.

## Risks
- Two-way sync can loop or conflict; define a clear precedence (Frappe status wins;
  bot Telegram identity wins) and never overwrite the other side's owned fields.
- Network/availability: bot and Frappe may be up independently — make sync retry-safe, not
  fire-and-forget.

## Implementation notes (2026-07-30)

### Endpoints (`klik_pos/api/driver.py`)
All four endpoints from the spec, following the `delivery.py` conventions (whitelisted, not
`allow_guest`, try/except returning `{"success": False, "message": ...}` on `ValidationError` and
generic `Exception`, `frappe.log_error` for the latter):
- `list_drivers(status=None, search="", start=0, limit=100)` — same pagination shape as
  `get_delivery_reports`, sorted by `modified desc` (not `creation desc`) so bot polling for
  recent status changes is cheap.
- `upsert_driver(data)` — create/update by optional `data.name`. Only writes `driver_name` /
  `phone_number` / `status`; silently ignores any Telegram-identity keys passed in `data` (they're
  bot-owned, see precedence below) rather than erroring, so a UI form that happens to echo back
  the full record on submit can't accidentally clobber identity.
- `set_driver_status(driver, status)` — approve/reject/suspend. No separate "Suspended" state
  exists (Todo 025's Select is Pending/Active/Rejected, mirroring the bot's 3-state model), so
  suspending an Active driver reuses `Rejected` — documented in the docstring so this isn't
  mistaken for a bug later.
- `sync_driver_from_bot(payload)` — matches on `bot_driver_id` first, falls back to
  `telegram_user_id`, else creates a new `Pending` driver. Only ever writes
  `bot_driver_id`/`telegram_user_id`/`telegram_username`/`chat_id` — never `driver_name` on an
  *existing* match (only sets a placeholder `driver_name` when creating a brand-new record, so
  first-contact signups aren't nameless).

### Sync direction: "bot polls" chosen over webhook (2026-07-30)
The spec's KlikPOS→bot direction said "webhook or the bot polls" — picked **polling** via
`list_drivers`, since every other bot↔KlikPOS integration point in this project (Todo 021/023) is
bot-initiated HTTP calls into KlikPOS; there's no existing webhook/push infrastructure in either
direction to reuse, and adding one would mean guessing at a bot-side callback URL/auth scheme this
repo doesn't own. `list_drivers(status=..., ...)` sorted by `modified desc` is enough for the bot
to poll "what changed since I last checked." Documented here since Todo 026 named this an open
choice.

### Verified via `bench execute` (scratch script, deleted after)
- Create (Pending) → approve (Active) → bot sync attaches Telegram identity to a *new* record
  (no existing `bot_driver_id`/`telegram_user_id` match) → re-sync with the same `bot_driver_id`
  updates in place (`created: False`), not a duplicate.
- Precedence proven directly: after a human renames a bot-created driver via `upsert_driver`, a
  follow-up `sync_driver_from_bot` call changes `telegram_username` but leaves `driver_name`
  exactly as the human set it.
- Two drivers with blank `phone_number` both insert cleanly (same nullable-unique behavior
  confirmed in Todo 025).
- Duplicate `phone_number` on a third driver correctly fails closed (`success: False`) rather than
  silently overwriting - though see note below on the error message.

### Known wrinkle (not fixed, out of scope): unfriendly duplicate-key message
This bench environment uses `mysqlclient` (`MySQLdb`), not `pymysql`. Frappe's
`is_unique_key_violation()` (`frappe/database/mariadb/database.py`) type-checks against
`pymysql.Error`, so on this environment it doesn't recognize a `MySQLdb.IntegrityError` and falls
through to `raise` instead of Frappe's friendly `"{field} must be unique"` message. The duplicate
is still correctly rejected (caught by this endpoint's own generic `except Exception`), just with
a raw MySQL error string in `message` instead of Frappe's normal wording. Pre-existing
environment/driver mismatch in Frappe core, not something introduced here or specific to Delivery
Driver - not fixed as part of this todo.
