# Todo 045: Self Pickup Status + Void Page Marker (Data Model)

**Status:** ✅ Done

## Description
Data-model foundation for Module 17's daily reconciliation checklist (see
[phase-16.md](../phases/phase-16.md)). Two additions: a `Self Pickup` outcome on Sales Invoice
(distinct from a delivery, per the user's real workflow - POS invoices are created *before*
fulfillment now, so "invoice exists" was never proof a page was resolved), and a void marker on
the booklet itself (paper page written, sale cancelled/never happened).

## Files Changed
- `klik_pos/klik_pos/custom/sales_invoice.json` + `klik_pos/setup/install.py`
  (`ensure_delivery_reconciliation_fields`) - `custom_delivery_status` options gain `Self Pickup`
- `klik_pos/klik_pos/doctype/delivery_booklet_void_entry/` (new child table: page_number, reason,
  voided_by, voided_at)
- `klik_pos/klik_pos/doctype/delivery_booklet/delivery_booklet.json` (`void_entries` Table field)
- `klik_pos/api/booklet.py` (`mark_page_void`, `unmark_page_void`, `_find_covering_booklet`)

## Implementation notes (2026-08-02)

### The `custom_delivery_status` options edit didn't apply via `bench migrate` alone
Editing `klik_pos/klik_pos/custom/sales_invoice.json` and running `bench migrate` silently did
**not** update the live Custom Field's `options` - `frappe.db.get_value("Custom Field", ...,
"options")` still showed the old 4-option list afterward. Root cause: this field (and the rest of
the Delivery Reconciliation fields) is actually managed by
`klik_pos.setup.install.ensure_delivery_reconciliation_fields()`, called from `after_migrate` via
`create_custom_fields(..., update=True)` - that function's own inline field definitions are the
real source of truth, not the `custom/sales_invoice.json` export (which the sync step apparently
doesn't treat as authoritative for property *updates* on an existing field, only creation). Fixed
by editing both places and re-running `ensure_delivery_reconciliation_fields()` directly (`bench
execute klik_pos.setup.install.ensure_delivery_reconciliation_fields`) to confirm. Worth
remembering for any future edit to a field this function manages - the JSON fixture alone is not
enough.

### Void marking auto-resolves its booklet
`mark_page_void`/`unmark_page_void` take just a page number - no booklet id - and look up the
covering booklet the same way ingestion matching does (any status, not just open ones, since a
void mark can land on a since-closed booklet's range too). Throws a clear error if no booklet is
registered for that range (booklet registration is a prerequisite for the whole feature).

### Live verification
`bench console` against `hd.phirun.me`: created a test booklet, marked/unmarked a page void
(including idempotent re-mark), confirmed void-on-unregistered-number fails cleanly. All test data
cleaned up after.
