# Todo 043: Bot-Side Booklet Status Poll + Telegram Alerts

**Status:** ✅ Done (logic verified in the bot's own venv; not yet run against a live Telegram bot
process - see Known gaps below)

## Description
The half of Module 16 that lives in `hd-delivery-telegram`, not this repo: turns the status
`check_booklet_lifecycle` (Todo 042) computes into the same Telegram alerts
`booklet-lifecycle.service.ts` used to send from the (still-live, Postgres-backed) NestJS
dashboard - "🚨 Booklet #N is STALLED!" / "...READY FOR REVIEW!", broadcast to the reporting chat
and DMed to every admin.

**Alert direction, decided with the user (2026-08-02):** the bot polls KlikPOS, not the reverse.
`driver_sync.py` (Phase 10 addendum) already established this precedent for KlikPOS-owned state
reaching the bot - no inbound HTTP surface exists on the bot at all today. A klik_pos → bot webhook
was the user's first instinct, but was dropped in favor of matching the existing pattern once
pointed out: it would have meant klik_pos holding the bot's address/a shared secret, and the bot's
first-ever inbound HTTP endpoint, for one feature.

## Implementation notes (2026-08-02)

### Transition detection, not level-triggered
`check_booklet_lifecycle` (klik_pos) only *sets* status - it doesn't remember whether a bot
already alerted on it. `booklet_sync.py` owns that memory itself (the new SQLite
`booklet_status` table): each poll pass records the last-seen status per booklet, and only sends
an alert when the *current* status differs from what was last seen AND is in `{Stalled, Ready for
Review}`. Without this, every 300s poll while a booklet sits in Stalled would re-send the same
alert forever - the original NestJS cron only notified on the transition itself, and this matches
that behavior despite polling on a fixed interval rather than reacting to an event.

### Deliberately stateless module (matches driver_sync.py)
`booklet_sync.py` takes `bot`/`admin_telegram_ids`/`reporting_chat_id`/`reporting_topic_id` as
parameters rather than importing `bot.py`'s globals directly, avoiding a circular import - same
reasoning `driver_sync.py`'s own docstring already gives for its shape. `booklet_poll_loop` (in
`bot.py`) re-reads `load_admin_ids()`/`get_reporting_config()` on every pass so a mid-run Settings
change takes effect without a bot restart.

### Verification
No live bot process was started (out of scope here - the bot's `.env`/token/running instance is
the user's to manage). Verified instead by:
- `python -m py_compile` on all touched files, plus AST-parsing and an actual `import bot` /
  `import booklet_sync` in the bot's own venv (`delivery-bot/venv`) - confirms the new module and
  its wiring into `bot.py` don't break anything at import time.
- A standalone script exercising `_check_one_booklet` directly against a fake `Bot`/real
  `local_store` (temp SQLite): confirmed the first Stalled observation alerts (broadcast + DM),
  a repeated Stalled poll does *not* re-alert, a transition to Ready for Review alerts again, and
  an Active status never alerts.

## Known gaps (not bugs - deliberately unverified so far)
- Never run against a real Telegram bot process or the actual `hd.phirun.me` KlikPOS instance
  together - the poll's `httpx` call to `klik_pos.api.booklet.list_booklets` and the eventual
  `bot.send_message` calls are each verified separately (Todo 041/042's live bench-console tests
  cover the endpoint; this todo's fake-bot script covers the alert logic), not end-to-end through
  an actual running bot.
- `BOOKLET_POLL_INTERVAL_SECONDS` (default 300s) is a guess, not tuned against real usage.
