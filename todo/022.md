# Todo 022: Auto-Match Logic with Confidence Scoring

**Status:** ✅ Done

## Description
Given a Delivery Report's fields — **already extracted and OCR-resolved by the bot** (invoice
number, amount, customer, driver, delivery status; see phase-09 "System boundary") — find the
most likely Sales Invoice and assign a confidence score. This is **structured-to-structured**
matching only: KlikPOS performs **no OCR/AI** (the bot did that). It is a **suggestion engine** —
it never mutates the invoice. It sets `matched_invoice`, `match_confidence`, and moves
`reconciliation_status` from `Unmatched` to `Suggested` when a candidate is found.

## Estimated Time
2-3 hours

## Files to Change
- `klik_pos/api/delivery.py` (MODIFY — add `match_delivery_report(report)` and helpers)

## Matching Strategy (highest confidence first)
1. **Exact invoice number**: `reported_invoice_no` == Sales Invoice `name` (or `custom_invoice_ref`).
   → confidence ~1.0.
2. **Fuzzy invoice number**: normalized/trimmed/typo-tolerant match on invoice no.
   → high confidence, needs review.
3. **Attribute match** when invoice no is missing/wrong: score candidates by
   customer + outstanding amount ≈ `amount_collected` + posting date near `delivery_timestamp`
   + driver == `custom_delivery_personnel`.
   → confidence from weighted field agreement.
- Prefer invoices that are **Unpaid / Partly Paid** and not yet delivered when scoring ties.

## Acceptance Criteria
- Exact invoice-number matches score at/near 1.0 and set status `Suggested`.
- When no candidate crosses a minimum threshold, `matched_invoice` stays empty and status
  remains `Unmatched`.
- The function is pure/read-only with respect to Sales Invoices — it writes only to the
  Delivery Report record.
- Confidence is deterministic and explainable (store which signals matched, e.g. in a notes or
  JSON field), so the reconciliation UI can show *why* it matched.

## Dependencies
- Todo 019 (Delivery Report fields)
- Todo 020 (so it can prefer not-yet-delivered invoices)

## Risks
- Fuzzy matching false positives are the main danger — bias toward leaving as `Unmatched` when
  uncertain rather than suggesting a wrong invoice.
- Amount matching must use `outstanding_amount` (not `grand_total`) for partial/credit invoices
  from Phase 1, or collected-cash amounts won't line up.

## Scope decision (2026-07-30) — attribute matching dropped
Before implementing, checked what data `Delivery Report` (Todo 019) actually captures from the
bot against what this todo's "Attribute match" tier needs (customer + amount + timestamp +
driver) — two of the four don't exist: the bot never reports a customer, and `amount_collected` is
explicitly a KlikPOS-side field filled in by a human during confirm (Todo 023), not by the bot, so
it's empty at auto-match time (which runs at ingestion). Asked the user how to handle this;
decided to **implement invoice-number matching only** (exact / normalized / fuzzy) and leave
Unmatched when the invoice number itself doesn't resolve — no attribute-based fallback attempted
with only 2 of 4 signals available, since driver+timestamp alone risked exactly the false-positive
suggestions the Risks section above warns against.

## Implementation notes (2026-07-30)
Implemented in `klik_pos/api/delivery.py`, replacing Todo 021's exact-match-only stub:
1. **Tier 1 (verbatim exact, confidence 1.0)**: matches `reported_invoice_no` against Sales
   Invoice `name` or `custom_invoice_ref`, unbounded (cheap indexed lookup, no date window
   needed).
2. **Tier 2 (normalized, confidence 0.92)**: strips everything but letters/digits and
   upper-cases both sides before comparing — tolerant of case, dashes, spaces
   ("acc sinv 2026 00021" still matches "ACC-SINV-2026-00021").
3. **Tier 3 (fuzzy, confidence 0.6–0.85)**: `difflib.SequenceMatcher` similarity ratio against a
   **bounded** pool (submitted invoices from the last 30 days) — tiers 2/3 run in Python since
   normalization/similarity aren't expressible in SQL, so the pool has to stay small; a rolling
   window is the natural bound given there's no customer/amount signal to narrow the search
   instead. Below 0.6 similarity, stays `Unmatched` (bias toward not guessing, per the Risks
   note).
- **Tie-break**: `_prefer_undelivered_unpaid()` — among equally-scored candidates, prefers
  invoices with `outstanding_amount > 0` and `custom_delivery_status != Delivered`, per this
  todo's tie-break rule.
- **Explainability**: added a new `match_notes` (Small Text, read-only) field to the `Delivery
  Report` doctype itself (edited its own doctype json directly + `bench migrate` — it's a fully
  owned doctype, not a customization of a foreign one, so no `create_custom_field`/patch needed)
  recording which tier/signal matched, e.g. `"Fuzzy invoice number match (similarity 0.93)"`.
- **Never touches already-decided reports**: `match_delivery_report` now refuses to run (returns
  immediately) if `reconciliation_status` is already `Confirmed` or `Rejected` — a human decision
  must never be silently overwritten by a later re-match call (Todo 023's manual re-match reuses
  this same function on unresolved reports only).

### Bug found and fixed while testing: `custom_invoice_ref` is an Int, not text
First draft's tier 1 queried `custom_invoice_ref` with a raw string filter
(`frappe.db.get_value("Sales Invoice", {"custom_invoice_ref": reported_no}, "name")`). Testing with
a garbage invoice number (`"ZZZZZZZZZZZZZZZZZZZZ"`) exposed that this field is actually `fieldtype:
Int` (DB column `int(11) NOT NULL DEFAULT 0`), so MySQL coerced the non-numeric string to `0` for
the comparison and matched the first invoice still at the untouched `0` default — a false "exact
match" on completely garbage input. Fixed via `_safe_nonzero_int()`: only queries
`custom_invoice_ref` when `reported_no` itself parses as a non-zero integer. Logged as
[BUG-002](../bugs.md) since this is a pre-existing landmine any other code querying that field by
string would also hit — not something to silently paper over only here.

Also caught and fixed a related latent crash in `_normalize_invoice_no` (`.upper()` called
directly on `value`, which would `AttributeError` the moment a real non-zero int
`custom_invoice_ref` reached tier 2/3 — masked in testing so far because every invoice in this
dataset still has the `0` default, which is falsy and short-circuits before `.upper()` is ever
called) — fixed by `str()`-casting first.

Verified via `bench console` against real invoices (30-day window):
- Exact match → confidence 1.0, `"Exact invoice number match"`.
- Case/dash-messy input (`"acc sinv 2026 00021"`) → confidence 0.92, normalized-match note.
- Truncated/typo input → fuzzy match at 0.85 (capped), correctly tie-broken toward the
  still-outstanding invoice when multiple candidates share the same prefix.
- Garbage string and numeric-but-wrong input → both correctly stay `Unmatched` (confirms the
  Int-coercion bug is actually fixed, not just no-longer-observed).
- Re-running `match_delivery_report` on a report already `Confirmed` leaves it completely
  untouched (guard confirmed).
- All test records cleaned up after verification.
