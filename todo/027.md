# Todo 027: Frontend Driver Management Page

**Status:** ⬜ Not started

## Description
A KlikPOS SPA page (new side-menu item) to list, create, approve/reject, and suspend drivers —
the native port of the bot's `/drivers` screen, tied into the Frappe `Driver` master.

## Estimated Time
2-3 hours

## Files to Change
- `klik_spa/src/pages/DriverManagementPage.tsx` (New)
- `klik_spa/src/services/driver.ts` (New — API client for Todo 026)
- `klik_spa/src/types/index.ts` or `klik_spa/types/index.ts` (MODIFY — `Driver` interface)
- Side menu / routing registration (wherever KlikPOS nav + routes are defined)

## UI Requirements
- Driver list with status badges (Active / Pending / Rejected), search, and filter by status.
- Create/edit driver form (name, phone, Telegram fields optional).
- Approve / Reject / Suspend actions with confirmation.
- Show Telegram linkage state (linked `@username` / id, or "not yet linked" when the bot hasn't
  synced identity).
- Pending-driver count badge on the nav item so new bot signups are visible.

## Acceptance Criteria
- Approving a `Pending` driver flips status to `Active` and it becomes selectable in delivery
  driver Link fields (Todo 028).
- Create/edit/status changes persist via the Todo 026 API and refresh the list.
- Matches KlikPOS styling/nav conventions (Tailwind v3, react-router, existing side menu), not the
  bot's Next.js/Tailwind v4 styles.
- `npm run build` passes with no TypeScript errors.

## Dependencies
- Todo 025, 026

## Risks
- Do not copy the bot's Next.js components verbatim — Tailwind v4 classes and Next-specific imports
  (`next/*`, server components) will not compile in the Vite SPA; port the markup/logic.
- Keep this page's scope to driver management; embedding the heavier bot screens (live map,
  conflicts) is a separate integration decision (Approach A / embed).
