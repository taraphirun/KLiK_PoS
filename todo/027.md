# Todo 027: Frontend Delivery Driver Management Page

**Status:** ✅ Done (`tsc --noEmit` clean, `yarn build` clean; not yet visually checked in a live
browser — no browser tool available this session, same caveat as Todo 024)

## Description
A KlikPOS SPA page (new side-menu item) to list, create, approve/reject, and suspend drivers —
the native port of the bot's `/drivers` screen, tied into the Frappe `Delivery Driver` master.

## Estimated Time
2-3 hours

## Files to Change
- `klik_spa/src/pages/DriverManagementPage.tsx` (New)
- `klik_spa/src/services/driver.ts` (New — API client for Todo 026)
- `klik_spa/src/types/index.ts` or `klik_spa/types/index.ts` (MODIFY — `DeliveryDriver` interface)
- Side menu / routing registration (wherever KlikPOS nav + routes are defined)

## UI Requirements
- Driver list with status badges (Active / Pending / Rejected), search, and filter by status.
- Create/edit driver form (name, phone, Telegram fields optional).
- Approve / Reject / Suspend actions with confirmation.
- Show Telegram linkage state (linked `@username` / id, or "not yet linked" when the bot hasn't
  synced identity).
- Pending-driver count badge on the nav item so new bot signups are visible.

## Acceptance Criteria
- Approving a `Pending` driver flips status to `Active` and it becomes selectable in delivery
  driver Link fields (Todo 028).
- Create/edit/status changes persist via the Todo 026 API and refresh the list.
- Matches KlikPOS styling/nav conventions (Tailwind v3, react-router, existing side menu), not the
  bot's Next.js/Tailwind v4 styles.
- `npm run build` passes with no TypeScript errors.

## Dependencies

## Risks

## Implementation notes (2026-07-30)

### Frontend
- `klik_spa/src/services/driver.ts` (new) - typed client for `list_drivers`, `upsert_driver`,
  `set_driver_status` (Todo 026). `DeliveryDriver` interface lives here, not in the shared
  `types/index.ts`, matching the `DeliveryReport`/`delivery.ts` precedent from Todo 024.
  `sync_driver_from_bot` has no frontend client - it's bot-only.
- `klik_spa/src/pages/DriverManagementPage.tsx` (new) - status-filter tabs (All/Pending/Active/
  Rejected), search, a card per driver showing phone number and Telegram linkage state (`@handle`
  if `telegram_user_id` is set, "Not yet linked to Telegram" otherwise), Edit/Approve/Suspend-or-
  Reject actions. Reuses the existing `components/ui/ConfirmDialog` for the approve/suspend/reject
  confirmation step (UI requirement) rather than a bespoke dialog. "Suspend" vs "Reject" label
  switches based on the driver's current status (Active -> "Suspend", Pending -> "Reject") since
  both map to the same `Rejected` status server-side (Todo 026 note).
- Create/edit form is a modal (`DriverFormDialog`) editing only `driver_name`/`phone_number` -
  Telegram fields are display-only here (bot-owned, per Todo 026 precedence), matching the "create/
  edit driver form (name, phone, Telegram fields optional)" requirement by making them optional
  *for the bot to fill in*, not human-editable.
- Routed at `/drivers` (`router/index.tsx`).
- Nav: added to both `RetailSidebar.tsx` (desktop) and `BottomNavigation.tsx` (mobile), gated
  behind the same `is_admin_user` flag as Deliveries (Delivery Driver's only DocType permission is
  System Manager, same reasoning as Todo 024). Desktop sidebar also polls
  `getDrivers("Pending")` every 60s for a pending-count badge on the icon, generalizing the
  existing single-purpose `showPendingBadge` boolean into a `badgeCount` that picks the right
  counter per nav path (Deliveries vs Drivers) rather than duplicating the badge-rendering JSX.
