## Implementation notes (2026-07-31)

### API key: POS Profile field, not a new config surface (decided with the user)
Added `custom_google_maps_api_key` (Data, not Password - a Maps JS key is meant to run
client-side, restricted by HTTP referrer in Google Cloud Console rather than treated as a server
secret) to POS Profile via `ensure_google_maps_api_key_field()` in `klik_pos/setup/install.py`
(+ matching `patches/v16_0/add_google_maps_api_key_field.py`), same dual pattern as
`ensure_pos_print_format_field`. Not exported to `custom/pos_profile.json` - checked first, and
that fixture doesn't mirror `custom_pos_printformat` either, so POS Profile custom fields in this
app are install.py/patch-only, unlike Sales Invoice's fields which do get fixture-exported.
Read on the frontend via the existing `posDetails` (POS Profile `as_dict()` already returns every
field, custom or not - no backend endpoint changes needed) - added
`custom_google_maps_api_key?: string` to the `POSProfile` type (`klik_spa/types/index.ts`).

### Realtime socket client (new infrastructure - first use in this app)
`klik_spa/src/utils/realtime.ts` connects via `socket.io-client`, deliberately mirroring
`frappe/public/js/frappe/socketio_client.js`'s `get_host()` (read directly from this bench's
Frappe source, not guessed): production connects to `window.location.origin` and relies on
nginx's standard Frappe proxy for `/socket.io` (this SPA has no `frappe.boot`, so there's no
`sitename`/`socketio_port` to read - uses `window.location.hostname` as the namespace, matching
Desk's convention for a `dns_multitenant` site accessed by its real domain). Dev-server fallback
(`import.meta.env.DEV`) connects directly to `hostname:9000` (the default `socketio_port`) since
Vite's dev server runs on a different port than the Frappe site itself.
`subscribeToDeliveryUpdates()` (`delivery.ts`) wraps this with the `delivery_report_update` event
name and returns an unsubscribe function.

### Map implementation
`LiveDeliveryMapPage.tsx` uses `@vis.gl/react-google-maps`'s legacy `Marker` (not
`AdvancedMarker`) - deliberately avoids requiring a Google Cloud "Map ID" as a second piece of
required config beyond the API key alone. Status-colored pins use Google's long-standing hosted
colored-dot icons (`maps.google.com/mapfiles/ms/icons/{color}-dot.png`) rather than shipping
custom marker assets. Initial load calls the existing `get_delivery_reports` across all statuses
(limit 200); live updates upsert into the same in-memory pin map by report name, so a reconcile
action's realtime event updates an existing pin's color/status without a refetch. Clicking a pin
opens an `InfoWindow` with driver/status/invoice and links out to `/invoice/:id` and
`/deliveries/reconcile` rather than re-implementing Confirm/Reject/Re-match inline - those actions
already exist on the reconciliation page (Todo 024) and duplicating that stateful logic here
wasn't worth it for a v1 map.

### Fix (2026-07-31): map rendered zoomed-in, offset toward the bottom-right
Reported by the user after adding a real API key. Root cause: classic flexbox + Google Maps
container-sizing bug. The map lived in a `<div className="relative flex-1">` inside a
`flex h-screen flex-col` page, with the `<Map>` itself sized via `style={{width:"100%",
height:"100%"}}`. A `flex-1` item's default `min-height: auto` means it won't reliably shrink to
the space actually left after the header - and Google Maps measures its container via
`getBoundingClientRect()` at mount, so an ambiguous/late-resolving percentage height initializes
the map against the wrong (smaller) size; the SDK doesn't always self-correct after the fact,
leaving tiles rendered zoomed-in and anchored to one corner instead of filling the box. Fixed by
(1) adding `min-h-0` to the flex-1 wrapper so it actually shrinks to the available space, and (2)
switching the map's own wrapper to `absolute inset-0` (anchored to the `relative` parent's actual
box) instead of a `height:100%` flowing through a flex child - deterministic regardless of flex
layout timing. `tsc`/`yarn build` clean; not yet re-confirmed by the user in the browser.

### Redesign (2026-07-31): ported UX patterns from the bot's own live map
User pointed at `hd-delivery-telegram/frontend/src/components/{DeliveryMap,MapFilters,LiveFeed}.tsx`
and `frontend/src/app/live/page.tsx` (cloned to `/home/frappe/dev/hd-delivery-telegram` for this) as
UI they find usable, and asked to adopt specific patterns from it (confirmed one-by-one rather than
ported wholesale):
- **Split layout**: map (`flex-1`) + a fixed-width (`360px`) right sidebar with Filters and a Live
  Feed section, replacing the earlier top-toolbar-plus-full-width-map layout. Their own
  `app/live/page.tsx` uses the exact same `flex-1 min-h-0` pattern this todo's zoom bug fix landed
  on independently - good confirmation the fix was right.
- **Distance-based clustering**: `buildClusters()` ports their nearest-cluster-append algorithm
  (haversine distance, 75m radius) rather than adding a clustering library. Cluster marker color
  is picked by priority (`STATUS_PRIORITY`: Unmatched > Suggested > Rejected > Confirmed) instead
  of their "cluster age in days" scheme - status urgency is the meaningful axis here, not delivery
  age, mirroring the same priority order the reconciliation queue's grouping already uses
  (2026-07-31 addendum, phase-09.md). Multi-item clusters show a count badge.
- **Custom map controls + slide-up detail panel**: `disableDefaultUI` + a floating control stack
  (map type toggle, recenter, zoom +/-) replaces Google's default chrome. Clicking a cluster opens
  a bottom slide-up panel listing every delivery in that cluster (horizontally scrollable cards),
  replacing the earlier single-pin `InfoWindow` - necessary once multiple deliveries can share one
  marker.
- **Filters**: added driver select (populated from currently-loaded pins) and invoice search
  alongside the existing status chips, plus a date range (native `<input type="date">`, not their
  Popover+react-day-picker Calendar - would've pulled in two more dependencies for a secondary
  filter). Date filtering is client-side over the already-fetched pin set (same as their
  implementation, which also filters client-side over its fetched batch) - no backend change,
  `get_delivery_reports` doesn't support date filters and didn't need to gain them for this.

### Deliberately not ported
- **Marker icon style**: kept `Marker` + `google.maps.Symbol` (colored circle + text label for the
  count) instead of their `AdvancedMarker`/`Pin`, which requires a Google Cloud "Map ID" as a
  second required config item beyond the API key - avoided per the earlier decision not to add
  that second config surface. Visually close enough (colored circle with a count badge) without it.
- **Fly-to camera animation and confetti**: their `flyTo()` (eased `requestAnimationFrame` pan/
  zoom) and `canvas-confetti` celebration on new deliveries are polish, not something asked about -
  skipped to keep this pass scoped to the four things actually confirmed (layout, clustering,
  controls/panel, filters). Easy follow-up if wanted later.
- **Backend payload additions**: `reported_invoice_no` and `delivery_timestamp` were added to the
  `on_update` realtime payload (`delivery_report.py`) and `DeliveryRealtimeUpdate`
  (`delivery.ts`) to support the invoice search and date-range filters - the only backend change
  this redesign needed.

### Deviations / known limitations (not fixed here)
- **No marker clustering.** "Clustering when dense" wasn't implemented - would need another
  dependency (`@googlemaps/markerclusterer`) and can't be visually tuned without a browser. Fine
  at low delivery volume; revisit if the demo data or real usage shows pins overlapping.
- **No route-level code splitting.** The Risks section flagged lazy-loading this route so the map
  SDK doesn't bloat the main bundle - not done, because *no* route in this app is code-split
  today (single main chunk, already >500kB before this todo). Splitting just this one route would
  be inconsistent with how the rest of the app is built for a marginal win; the bundle grew from
  ~1.52MB to ~1.62MB. Worth reconsidering only as part of a broader code-splitting pass, not
  bolted on for one page.
