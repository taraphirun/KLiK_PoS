# Todo 021: Bot Ingestion API Endpoint

**Status:** ✅ Done

## Description
Create a whitelisted endpoint the Telegram delivery bot calls to submit a delivery report.
It validates the payload, creates a `Delivery Report` staging record, and triggers the
auto-match attempt (Todo 022). It must be idempotent per bot message.

## Estimated Time
1-2 hours

## Files to Change
- `klik_pos/api/delivery.py` (New)
- `klik_pos/hooks.py` (only if a scheduler/permission wiring is needed)

## Endpoint
- `@frappe.whitelist() def submit_delivery_report(data)`:
  - Accepts: `bot_delivery_id`, `reported_invoice_no`, `completion_status`, `payment_status`,
    `delivery_driver`, `driver_telegram_id`, `delivery_timestamp`, `gps_latitude`, `gps_longitude`,
    and optional photo/voice file references (uploaded separately — see Phase 13 Todo).
  - Validates required fields and enum values (`completion_status` ∈ Full/Partial,
    `payment_status` ∈ Paid/Unpaid/Partial).
  - **Idempotent on `bot_delivery_id`**: return the existing record instead of creating a duplicate.
    This is what lets the bot's offline sync worker (Phase 13) re-send safely after downtime.
  - Stores the untouched payload in `raw_payload`.
  - Calls the auto-matcher (Todo 022) and saves the resulting `matched_invoice`,
    `match_confidence`, and `reconciliation_status`.
  - Returns the Delivery Report name, matched invoice (if any), and confidence — so the bot can
    record it as **Synced** in its local SQLite.

## Offline-first context (Phase 13)
This endpoint is the drain for the bot's store-and-forward queue: the bot writes deliveries to a
local SQLite store first (so drivers keep working when ERPNext is down), then a sync worker POSTs
unsynced rows here. Idempotency + a clear success response are therefore mandatory, not optional.

## Acceptance Criteria
- Valid payload creates exactly one `Delivery Report` and returns its identifiers.
- Re-posting the same `bot_delivery_id` returns the original record and creates no duplicate
  (verify under concurrent/rapid retries, the offline drain case).
- Invalid/missing required fields return a clear error without creating a record.
- Endpoint is authenticated (bot uses an API key / service user), not open to the public.

## Dependencies
- Todo 019 (Delivery Report DocType)
- Todo 022 (auto-match — can be stubbed first, wired after)

## Risks
- Authentication: the bot must use a scoped API key or dedicated user; do not expose this
  unauthenticated (`allow_guest`).
- Timestamp/timezone handling — normalize `delivery_timestamp` to site timezone on ingest; the
  bot may sync a delivery hours after it happened (offline), so trust the bot's timestamp over
  server-receive time.

## Implementation notes (2026-07-30)
Created `klik_pos/api/delivery.py` with `submit_delivery_report(data)`:
- Plain `@frappe.whitelist()` (no `allow_guest`) — this app has no existing role/permission-gating
  precedent for bot-style endpoints (checked; every other `allow_guest=True` endpoint in this app
  is used by the already-authenticated POS frontend session, not an external service), so the
  requirement to not expose this to the public is satisfied the standard Frappe way: the caller
  must authenticate (session or API key/secret) as a real Frappe user. Operationally this means
  giving the bot a dedicated user + API key with create-permission on Delivery Report — a
  deployment/config step, not something to enforce further in code.
- Validates required fields (`bot_delivery_id`, `reported_invoice_no`, `completion_status`,
  `payment_status`) and the two enums, via `frappe.throw` caught by the outer try/except and
  turned into `{"success": False, "message": ...}` — matches the existing error-response
  convention in this app (e.g. `validate_before_submit` in `sales_invoice.py`), no exception
  reaches the HTTP layer as a 500.
- Idempotency: checks for an existing record by `bot_delivery_id` first (fast path for the common
  retry case), and additionally catches `frappe.exceptions.UniqueValidationError` around the
  insert itself (the DB-level unique constraint from Todo 019 as the real backstop) and re-fetches
  the existing record instead of erroring — covers the concurrent/rapid-retry race the fast path
  alone can't.
- `delivery_timestamp` is parsed via `get_datetime()` from whatever the bot sent, not
  `frappe.utils.now()` — trusts the bot's reported time per the Risk note above.
- Added a minimal `match_delivery_report(report)` in the same file (exact `reported_invoice_no` ==
  Sales Invoice name only, confidence 1.0 → `Suggested`, else stays `Unmatched`) — this is the
  explicitly-allowed stub per this todo's Dependencies section; Todo 022 replaces it with real
  fuzzy/attribute matching. It mutates the in-memory `report` doc only, so it's called once before
  `insert()` (one write instead of insert-then-update).

Verified via `bench console` (`klik_pos.api.delivery.submit_delivery_report`) against a real
submitted invoice:
- Valid payload → creates exactly one Delivery Report, matches the real invoice
  (`match_confidence=1.0`, `reconciliation_status=Suggested`).
- Re-posting the identical payload → returns the same record (`Delivery Report` count for that
  `bot_delivery_id` stays at 1) — idempotency confirmed.
- Payload missing `reported_invoice_no` → `{"success": False, "message": "Missing required
  field(s): reported_invoice_no"}`, no record created.
- Payload with a `reported_invoice_no` that doesn't match any invoice → record created but stays
  `Unmatched`, `matched_invoice` empty.
- Test records cleaned up after verification.
