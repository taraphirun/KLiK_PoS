# Todo 033: Bot Local SQLite Store (Offline Capture)

**Status:** ✅ Done

## Description
Replace the bot's Postgres writes with a local SQLite store so every delivery is persisted on the
device/host immediately, independent of KlikPOS availability. This is the durable outbox for
store-and-forward sync.

## Estimated Time
2-3 hours

## Files to Change (in `hd-delivery-telegram/delivery-bot`)
- `bot.py` (MODIFY — swap asyncpg `delivery_logs` writes for SQLite)
- new local `deliveries.sqlite` schema + a small data-access module

## Schema (mirror `delivery_logs` + sync state)
- `bot_delivery_id` (TEXT/UUID, PK) — idempotency key sent to KlikPOS
- `reported_invoice_no`, `completion_status` (Full/Partial), `payment_status` (Paid/Unpaid/Partial)
- `latitude`, `longitude`, `driver_id`, `driver_name`, `timestamp`
- `photo_paths` (JSON — local file paths), `voice_path` (TEXT)
- `sync_status` (TEXT: `Not Synced` / `Synced` / `Failed`) — default `Not Synced`
- `synced_delivery_report` (TEXT) — KlikPOS Delivery Report name after sync
- `last_sync_error` (TEXT), `sync_attempts` (INT), `created_at`, `updated_at`

## Acceptance Criteria
- Completing the FSM flow writes one SQLite row with `sync_status = Not Synced`, even with no
  network / KlikPOS down.
- The driver's flow completes normally offline (no errors, delivery is saved).
- Drivers can list their recent deliveries with a Synced / Not Synced indicator.
- `bot_delivery_id` is generated once at capture and never changes (stable idempotency key).

## Dependencies
- None (bot-side foundational); pairs with Todo 034.

## Risks
- Concurrency: aiogram is async — use a single writer / WAL mode to avoid SQLite lock errors.
- Local disk durability — SQLite file must be on persistent storage, not a container tmpfs.

## Implementation notes (2026-07-31, in `hd-delivery-telegram`)

### The plan's tech-stack assumption was briefly wrong, then corrected
When this todo was picked up, the bot repo's `main` branch had no `delivery-bot/` directory at
all - the driver-facing flow was still the old photo+OCR pipeline (NestJS/Telegraf/Prisma/
BullMQ), not the aiogram FSM this todo assumed. The user had a newer branch with the FSM bot
already built (a "v2" pivot, `saved_plan/implementation_plan.md` in that repo) - pulling it
brought in exactly the `delivery-bot/bot.py` (aiogram, asyncpg, Redis, MinIO) this todo's file
paths already expected. Worth recording since it briefly looked like the whole Phase 9 "no OCR/
AI" system boundary was inaccurate; it wasn't, the repo just hadn't been pulled yet.

### SQLite outbox (`delivery-bot/local_store.py`, new)
Schema matches this todo's spec exactly. `bot_delivery_id` is the primary key with
`ON CONFLICT DO NOTHING` on insert (idempotent, matching the same posture used everywhere else in
this integration) - `insert_delivery()` returns whether it actually inserted, so the caller can
tell a driver "already logged" vs "logged" without a separate existence check. WAL mode set on
every connection (a fresh `aiosqlite.connect()` per call, not one long-lived connection - aiogram
handlers run concurrently across drivers, and WAL mode is what lets that coexist without
"database is locked" errors, per this todo's own concurrency risk note).

### Capture ordering fix in `finalize_delivery()` (bot.py)
The existing code wrote to Postgres FIRST, with an early `return` on failure - bolting the SQLite
write on afterward (as originally sequenced) would have meant a Postgres outage still blocked
capture, defeating the entire point of "offline-first" per this phase's own stated objective.
Reordered: media downloads to local disk + the SQLite outbox write now happen first and are what
determines success/failure back to the driver; the legacy Postgres dual-write
(`delivery_bot.delivery_logs` + `public.Invoice`, kept for the NestJS dashboard during the
transition - decided with the user 2026-07-31, Todo 036 retires it later) is now best-effort,
wrapped so its failure is logged but never surfaced to the driver as "unable to save" - the
delivery is already durably captured by that point.

### Media buffering
Photos/voice are downloaded from Telegram to local disk synchronously in `finalize_delivery`
(new `download_media_locally()`), not deferred to sync time. This doesn't compromise offline-
first - that guarantee is about KlikPOS/network-to-Frappe reachability, not Telegram itself (the
bot can't be mid-conversation without a live Telegram connection regardless) - and means the sync
worker (Todo 034/035) only ever deals with local files, never Telegram `file_id`s that could
theoretically go stale by sync time.

### Known gap (not built, out of scope for this pass)
"Drivers can list their recent deliveries with a Synced/Not Synced indicator" (Acceptance
Criteria) was not implemented - only an *admin*-facing `/syncstatus` command exists (Todo 034),
showing aggregate pending/synced/failed counts, not a per-driver history view. Flagging as a
deliberate scope cut, not an oversight - the admin visibility was the higher-value piece for a
first pass.

### Verification
Logic-tested directly (insert, duplicate detection via the `inserted` return value, status-count
aggregation) via a throwaway script - see Todo 034's notes for the full end-to-end trace through
the sync worker against the real KlikPOS site.
