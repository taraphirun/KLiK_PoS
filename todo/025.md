# Todo 025: `Delivery Driver` DocType

**Status:** ✅ Done

## Naming note (2026-07-30)
ERPNext core already owns the doctype name `Driver` (`erpnext/setup/doctype/driver`, Setup
module — fleet/employee-oriented, `Fleet Manager`/`Delivery Manager` roles, Active/Suspended/Left
status tied to `Employee`/`Transporter`). Frappe doctype names are global, so this doctype is
named `Delivery Driver` instead. Only the *Frappe* doctype is renamed — the bot's own Postgres
`Driver` table (Prisma model) is a separate system and keeps its own name unchanged.

## Description
Create a Frappe `Delivery Driver` doctype that mirrors the delivery bot's driver model so drivers
can be referenced (Link) from Delivery Reports and Sales Invoices, and managed from KlikPOS.

## Estimated Time
1-2 hours

## Files to Change
- `klik_pos/klik_pos/doctype/delivery_driver/delivery_driver.json` (New)
- `klik_pos/klik_pos/doctype/delivery_driver/delivery_driver.py` (New)
- `klik_pos/klik_pos/doctype/delivery_driver/__init__.py` (New)

## Fields (mirror the bot's Prisma `Driver`)
- `driver_name` (Data, required) — the doctype `title` field
- `phone_number` (Data, unique)
- `telegram_user_id` (Data, unique) — set by the bot on first contact
- `telegram_username` (Data, unique)
- `chat_id` (Data) — Telegram chat id for bot messaging
- `status` (Select: Active / Pending / Rejected) — default Pending
- `bot_driver_id` (Data, unique) — the bot Postgres `Driver.id` (uuid), for cross-system sync

## Acceptance Criteria
- DocType installs cleanly with no schema errors.
- `status` defaults to `Pending`; only `Active` drivers are selectable in delivery driver Link
  fields (enforce via link filter in Todo 028).
- Unique constraints on `phone_number`, `telegram_user_id`, `telegram_username`, `bot_driver_id`
  prevent duplicates during sync.
- `bot_driver_id` allows a Frappe driver to be matched to its bot counterpart (and vice versa).

## Dependencies
- None (foundational for Phase 10)

## Risks
- Uniqueness on nullable Telegram fields: many drivers may have no Telegram yet — ensure unique
  constraints permit multiple NULL/empty values (Frappe unique allows multiple blanks, verify).
- Keep field names stable; Todo 028 and the bot sync bridge depend on them.

## Implementation notes (2026-07-30)
- Created `klik_pos/klik_pos/doctype/delivery_driver/` (`Delivery Driver` doctype, module `KLiK
  PoS`). `autoname: format:DRV-{####}`, `title_field: driver_name`, `status` Select
  (`Pending\nActive\nRejected`, default `Pending`, required). Fields grouped into a base section,
  a "Telegram Identity" section (`telegram_user_id`, `telegram_username`, `chat_id`), and a
  "Cross-System Sync" section (`bot_driver_id`) — mirrors `delivery_report.json`'s section-break
  style.
- `bench migrate` created the table cleanly, no schema errors.
- Verified the nullable-unique risk directly: inserted two `Delivery Driver` docs with blank
  `phone_number`/`telegram_user_id`/`telegram_username`/`bot_driver_id` in the same transaction —
  both succeeded. Frappe's `base_document.py` converts blank values on `unique` fields to `None`
  before the DB write (not `''`), so MySQL's unique index treats them as distinct NULLs rather
  than colliding duplicates — confirms the Risks note's assumption without needing a workaround.
- Link-field restriction to `status = Active` (mentioned in Acceptance Criteria) is Todo 028's
  job, once the Link fields themselves exist.
