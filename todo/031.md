# Todo 031: Realtime Delivery Events

**Status:** ✅ Done

## Description
Emit Frappe realtime events when a Delivery Report is created or its reconciliation state changes,
so the live map (and any open list) updates without polling.

## Estimated Time
1-2 hours

## Files to Change
- `klik_pos/klik_pos/doctype/delivery_report/delivery_report.py` (MODIFY — `on_update` / `after_insert`)
- `klik_pos/api/delivery.py` (MODIFY — emit on reconcile actions if not covered by doc events)

## Requirements
- On new Delivery Report (ingested via Todo 021) publish an event with the minimal map payload:
  id, lat/long, driver, completion + payment status, recon status.
- On reconcile (confirm/reject/re-match) publish an update event.
- Use a stable event name (e.g. `delivery_report_update`) and scope to the right user/role room.

## Acceptance Criteria
- Creating/reconciling a Delivery Report pushes an event the SPA can subscribe to.
- Payload is minimal (no photos/raw payload) to keep the socket light.
- No event on unrelated doctype saves.

## Dependencies
- Phase 9 (Todo 019, 021, 023)

## Risks
- Realtime room/permission scoping — don't broadcast delivery locations to unauthorized sessions.
- High delivery volume could be chatty; debounce or batch if needed.

## Implementation notes (2026-07-31)
- Implemented as a single `on_update` hook on `DeliveryReport`
  (`klik_pos/klik_pos/doctype/delivery_report/delivery_report.py`) rather than separately from
  `klik_pos/api/delivery.py` per-endpoint. `on_update` fires on both insert and every subsequent
  save (confirmed directly against Frappe's `Document.insert()`/`run_post_save_methods` source),
  so ingestion (Todo 021's `report.insert()`) and every reconcile action (confirm/reject/re-match,
  all end in `report.save()`) publish through the one hook with no duplication.
- Skips publishing entirely when `gps_latitude`/`gps_longitude` are unset - nothing for the map to
  plot, satisfies "no event on unrelated... saves" in spirit (a Delivery Report with no GPS is
  common - photos-only or manually-entered reports - and shouldn't be chatty for no reason).
- Payload: `name`, `gps_latitude/longitude`, `delivery_driver_name` (falls back to
  `reported_driver_name` when unresolved, same pattern as the reconciliation UI),
  `completion_status`, `payment_status`, `reconciliation_status`, `matched_invoice`. No photos/raw
  payload, per spec.
- Event name `delivery_report_update`, published via `frappe.publish_realtime(...,
  after_commit=True)` - `after_commit` avoids a race where a client receives the event and reads
  back a document whose transaction hasn't landed yet.
- Room/scoping (decided with the user 2026-07-31): broadcasts to all logged-in sessions (no
  `room`/`user` restriction), matching this module's existing authorization posture -
  `get_delivery_reports`/`confirm_delivery_match`/etc. already don't enforce a role check beyond
  "logged in," only the SPA nav hides these pages from non-admins. This isn't a new gap, but also
  doesn't close the pre-existing one; worth hardening later alongside the wider delivery API
  permission model if that's ever tightened.
- Verified via `bench execute`: monkeypatched `frappe.publish_realtime` to capture calls, then
  exercised `submit_delivery_report` (no GPS → no event; with GPS → exactly one event with the
  right payload and `after_commit=True`) and `reject_delivery_match` (confirms the hook re-fires
  on every save, not just insert). Frappe's own built-in `doc_update`/`list_update` realtime
  events fired alongside (unrelated, framework-level) - filtered out by event name in the test
  rather than asserting a bare call count. All test data cleaned up afterward.
