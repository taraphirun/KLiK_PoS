# Todo 012: Backend Additional Discount Field Wiring

**Status:** ✅ Done

## Description
Support an invoice-level "Additional Discount" (flat amount or percentage) in the POS checkout
flow. ERPNext core already fully implements this — Sales Invoice has native `discount_amount`,
`additional_discount_percentage`, and `apply_discount_on` (Grand Total/Net Total) fields, and
`calculate_taxes_and_totals()` (already invoked in `build_sales_invoice_doc`) already applies them
correctly, including against taxes. klik_pos currently never sets any of these fields.

The round-off half of the original Todo 012 is **already fixed** (commit `cf59278`,
2026-07-07 — klik's custom roundoff monkey-patch was removed in favor of ERPNext's native
rounding) and needs no further work.

## Estimated Time
30-45 minutes (reduced from original 45-60 since no discount/round-off math needs to be written)

## Files to Change
- `klik_pos/api/sales_invoice.py`

## Implementation Notes
- `parse_invoice_data`: read `additionalDiscountAmount` / `additionalDiscountPercentage` and an
  `apply_discount_on` (or `discountType`) hint from the payload, defaulting to no discount / "Grand
  Total" respectively.
- Implement `_set_additional_discount_fields(doc, discount_amount, discount_percentage, apply_discount_on)`:
  - Set exactly one of `doc.discount_amount` (flat) or `doc.additional_discount_percentage`
    (percentage) — mutually exclusive, matching core's own field semantics.
  - Set `doc.apply_discount_on` to `"Grand Total"` or `"Net Total"`.
  - Do not compute the discounted total by hand — `doc.calculate_taxes_and_totals()` (core) does
    that once these fields are set.
- Call this from `build_sales_invoice_doc` (before `calculate_taxes_and_totals()`) so it applies to
  both the real submit path and `validate_checkout_invoice`'s preview path identically.

## Dependencies
- None

## Acceptance Criteria
- `_set_additional_discount_fields` only sets native erpnext fields, no custom discount math.
- Setting a discount amount/percentage produces the same `grand_total` via
  `validate_checkout_invoice` (preview) and the actual submitted invoice.
- Round-off remains untouched (`_set_roundoff_fields` stays a no-op).

## Risks
- Incorrect discount calculations can directly impact revenue and accounting records — mitigated by
  relying entirely on core's already-tested `calculate_taxes_and_totals()` instead of custom math.
