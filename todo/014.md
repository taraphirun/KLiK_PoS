# Todo 014: Batch the Per-Item Price Query in get_items()

**Status:** ✅ Done

## Description
Fix an N+1 query in `klik_pos.api.item.item_listing.get_items()`: the price-list priority
resolution (Customer → Customer Group → POS Profile → Selling Settings) is already correct and
already resolved once per request via `_get_priority_price_list()` — no changes needed there. But
`_fetch_item_prices_sql(item_code, price_list, current_date)` is called once per item **inside**
the product-grid loop, unlike stock/bundle/variant data in the same function which are already
batched before the loop (`_fetch_batch_stock`, `_fetch_product_bundle_map`,
`_fetch_variant_count_map`). With up to 2000 items per page, this is up to 2000 separate queries.

This replaces the originally-planned new `klik_pos/api/item/item_price.py` endpoint
(`get_items_prices_for_customer`) — that endpoint would have nothing calling it, since the frontend
already gets fully-priced items directly from `get_items()`'s response.

## Estimated Time
30-45 minutes

## Files to Change
- `klik_pos/api/item/item_listing.py`

## Implementation Notes
- Add `_fetch_item_prices_batch_sql(item_codes, price_list, current_date)`: single query with
  `item_code IN (...)`, same columns/filters as `_fetch_item_prices_sql`
  (`price_list_rate, currency, uom, batch_no, valid_from, valid_upto`), grouped into a
  `{item_code: [rows]}` dict.
- Call it once before `for item in items:` (alongside `stock_map`/`product_bundle_map`/
  `variant_count_map`), then replace the in-loop
  `item_prices = _fetch_item_prices_sql(item_code, price_list, current_date)` with
  `item_prices = item_prices_map.get(item_code, [])`.
- Leave `_fetch_item_prices_sql` (the single-item version) in place if anything else still calls it
  (e.g. `get_item_price_for_customer` in `item_price.py`) — only `get_items()`'s internal usage
  changes.

## Dependencies
- None

## Acceptance Criteria
- `get_items()` issues one price query per request (per page), not one per item.
- Returned prices are identical to before the change (same price-list priority, same UOM/date
  filtering) — this is a performance fix, not a pricing-logic change.

## Risks
- Must preserve the existing per-UOM/batch/valid-date row shape consumed later in the loop
  (`stock_uom_price`/`sales_uom_price` lookups by `uom`) — the batched query must return the same
  row shape, just grouped by item_code instead of filtered by a single item_code.
