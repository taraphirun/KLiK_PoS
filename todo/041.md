# Todo 041: Delivery Booklet Registry (DocType + CRUD + Ingestion Matching + Management UI)

**Status:** ✅ Done

## Description
Core registry piece of Module 16 (see [phase-15.md](../phases/phase-15.md) for the full
feasibility writeup). A `Delivery Booklet` is a physical paper invoice book: a number range,
optionally dedicated to one VIP customer. `submit_delivery_report` now resolves a report's
`reported_invoice_no` against the registry at ingestion time, same as it already does for Sales
Invoice matching.

## Implementation notes (2026-08-02)

### Matching logic (`match_booklet_for_invoice`)
Digits-only parse of `reported_invoice_no` (tolerant of prefixes like "INV-1234", mirrors the
NestJS `replace(/\D/g, '')` approach), then a range lookup. Prefers an open (non-Closed) booklet;
falls back to a Closed one only if the delivery's own timestamp is not after that booklet's
`closed_at` - a late-arriving sync for an already-closed booklet should still link correctly
rather than come up out-of-range. No match (but a numeric invoice number) sets
`is_booklet_out_of_range = 1` for manual resolution (Todo 044's reconciliation-page action).

### Renaming a booklet number
`Delivery Booklet` autonames by `field:booklet_number`, so `upsert_booklet` uses
`frappe.rename_doc` when an edit changes the number rather than a plain field assignment - Frappe
doesn't allow a Link'd field's autoname source to drift from the actual docname otherwise.

### Gap detection scope (deliberate, matches the original)
`get_booklet_gaps` only flags numbers strictly between the lowest and highest *reported* number
for that booklet - not the full start-end range, most of which is legitimately just not written
yet. This mirrors the NestJS dashboard's own deliberate definition (a real skipped/missing page,
not "not yet delivered").

### Live verification (bench console against hd.phirun.me)
Created test booklets (normal range, VIP range, a booklet whose end number was hit, one backdated
past the stall window), ran `submit_delivery_report` against in-range/VIP/out-of-range invoice
numbers, confirmed `resolve_booklet`/`get_candidate_booklets`/`get_booklet_gaps` /
`close_booklet`/`delete_booklet` (including the "can't delete a booklet with linked reports"
guard) all behave correctly, then deleted all test data. One real bug caught by this: the first
test pass showed every booklet as unmatched - `bench console` does not auto-commit on exit, so an
earlier `upsert_booklet` call's `doc.save()` was silently rolled back between console sessions.
Fixed by adding explicit `frappe.db.commit()` calls in the test scripts (not a code bug -
`upsert_booklet` itself already saves correctly in the real request/response cycle, which does
commit).
