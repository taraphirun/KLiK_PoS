# Todo 044: VIP Auto-Customer-Assign + Reconciliation Page Surfacing

**Status:** ✅ Done

## Description
The staff-facing payoff of Module 16: a Delivery Report matched to a VIP booklet suggests that
booklet's customer when backfilling an invoice (Todo 038's Create Invoice modal); an out-of-range
report gets a manual "link to a booklet" action right on the reconciliation page instead of
needing a trip to the new Booklets page.

  `booklet_status`, `booklet_customer`)
- `klik_spa/src/services/delivery.ts` (`DeliveryReport` interface: the new booklet fields)
- `klik_spa/src/pages/DeliveryReconciliationPage.tsx` (booklet badge + out-of-range badge on each

- `klik_spa/src/components/delivery/CreateInvoiceFromReportModal.tsx` (prefills `customer` from
  `report.booklet_customer` on open - a hint only, never overrides a customer already picked)

## Implementation notes (2026-08-02)

### Why `booklet_customer` is a hint, not an assignment
Unlike the original NestJS `db-save.processor.ts` (which assigns the customer unconditionally at
ingestion time, before any human looks at the delivery), KlikPOS surfaces it as a prefill in the
Create Invoice modal that staff can still change - consistent with this feature's own framing
throughout (`match_booklet_for_invoice`/`vip_customer_for_booklet`'s docstrings) as a suggestion,
never an authoritative write, since a booklet range collision or a one-off delivery to someone
else picking up for the VIP customer are both real possibilities the auto-assign shouldn't
silently paper over.

### Customer prefill mechanics
`CreateInvoiceFromReportModal` only has a `Customer` docname (`booklet_customer`) to work with,
but `CustomerSearchSection` needs a full `Customer`-shaped object for its `selectedCustomer` prop.
Resolved with a small `get_customers`-backed lookup (same endpoint the modal's item search already
calls directly, not through the shared `useCustomerStore`/`useCustomers` hook - consistent with
this modal's established pattern of avoiding the shared POS-checkout state for a screen that isn't
the checkout flow) into a minimal object literal cast `as Customer`, same pattern used in
`BookletsPage.tsx`'s own edit-form hydration - `tsc --noEmit` passes clean since the object's
present fields (`id`/`name`/`customerName`) legitimately overlap the `Customer` type.
