# Todo 052: Group Daily Checklist by Booklet Instead of One Day-Wide Range

**Status:** ✅ Done

## Description
Real bug reported by the user: with invoice 1222 and the next invoice 2222 both touched the same
day, the Daily Reconciliation checklist computed one `[min, max]` range across the *entire* day
(`[1222, 2222]`) and iterated all ~1000 numbers in between, flooding the page with fake
"Unresolved" rows for numbers that belong to completely unrelated (or unregistered) booklets.

## Files Changed
- `klik_pos/api/booklet.py` - `_resolve_booklet_bucket` (new), `_classify_number` (extracted),
  `_classify_daily_checklist` rewritten to return `(groups, counts)` instead of
  `(rows, start_number, end_number, counts)`; `_flatten_rows`/`_groups_summary` (new);
  `get_daily_reconciliation`/`close_daily_reconciliation`/`link_invoice_to_page` updated for the
  new shape
- `klik_pos/klik_pos/doctype/delivery_booklet_daily_closing/delivery_booklet_daily_closing.json` -
  `start_number`/`end_number` (Int) replaced with `groups_summary` (JSON) - a single day can now
  span multiple disjoint booklets, so one min/max pair is no longer enough to snapshot at close
  time or compare against for drift detection
- `klik_spa/src/services/booklet.ts` - `DailyGroup`/`ClosingGroupSummary` types,
  `DailyReconciliation.groups` replaces `.data`/`.start_number`/`.end_number`
- `klik_spa/src/pages/DailyReconciliationPage.tsx` - `BookletGroupCard` (new) renders one section

  that day

  Booklet form (the "Register this booklet" shortcut's target)

## Implementation notes (2026-08-02)

### Grouping key: real booklet if registered, else an implied bucket
`_resolve_booklet_bucket(number, pages_per_booklet, registered_booklets)` prefers an actual
registered `Delivery Booklet` (any status) covering the number. If none exists, it computes an
*implied* bucket: `idx = ceil(number / pages_per_booklet)`, range
`[(idx-1)*pages_per_booklet+1, idx*pages_per_booklet]` - sequential integer booklet numbering,
page 1 of booklet 1 = page number 1. Validated live against this shop's real registered booklets
before writing any code: booklet #45 covers exactly 2201-2250 with `pages_per_booklet=50`, which
is exactly what the formula predicts - confirming the anchor assumption was safe to build on
without needing to ask the user to confirm it separately.

### Per-group range is still interior-only, not the full 50-page booklet
Within one group, the checklist shows only the span between that group's own touched numbers
(e.g. just page 2222 if that's the only one touched in booklet #45 today) - not all 50 pages of
the booklet. Confirmed with the user before implementing: showing the full range every time would
reintroduce noise at a smaller scale, since most of an unfinished booklet is legitimately "not
written yet." Same interior-only philosophy `get_booklet_gaps` already uses.

### Close Day stayed one whole-day action (decided with the user)
Considered making each booklet group independently closeable, but the user confirmed "one whole-
day action" matches their mental model ("like daily account book closing"). The consequence:
`close_daily_reconciliation` still blocks until *every* group touched that day is resolved, and
the closing snapshot now stores a list of per-group ranges (`groups_summary` JSON) rather than one
pair - the drift-detection comparison in `get_daily_reconciliation` compares the whole list.

### Live verification (bench console against hd.phirun.me)
Recreated the exact reported scenario: invoices at 1222 (no registered booklet - implied booklet
"25", range 1201-1250) and 2222 (registered booklet #45, 2201-2250) on the same day produced
**2 groups**, each with a single-row interior span - zero fake gap rows, versus ~1000 before the
fix. Verified close (blocks until both groups resolve, stores both in `groups_summary`), drift
detection across a newly-appearing third group, and `link_invoice_to_page` respecting each group's
own interior span (correctly rejected linking to a number outside any touched span, succeeded once
a genuine interior gap existed). All test data cleaned up after (two cancelled-but-not-deleted
invoices left over due to this site's tight stock, same known limitation as before - not touched
per the standing "don't modify Stock Settings" instruction).
