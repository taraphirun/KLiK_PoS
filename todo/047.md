# Todo 047: Daily Reconciliation Checklist + Closing

**Status:** ✅ Done

## Description
The actual end-of-day workflow Module 17 exists for (see
[phase-16.md](../phases/phase-16.md) for the full design/decisions): every invoice/page number
touched on a given date, classified into one of seven states, with a hard-blocked "close the day"
sign-off once everything's accounted for - and detection when new data arrives for an
already-closed day.

## Files Changed
- `klik_pos/klik_pos/doctype/delivery_booklet_daily_closing/` (new doctype)
- `klik_pos/api/booklet.py`:
  - `_classify_daily_checklist(date)` - shared core: gathers `Sales Invoice.custom_invoice_ref`
    (posting_date = date) and `Delivery Report.reported_invoice_no` (delivery_timestamp/creation
    date = date), classifies every number in the resulting `[min, max]` range.
  - `get_daily_reconciliation(date=None)` - the read endpoint, plus the lazy re-review drift check.
  - `close_daily_reconciliation(date=None)` - hard-blocked, recomputes fresh rather than trusting
    a cached frontend response.
  - `reopen_daily_reconciliation(date=None)` - System Manager only.

## Implementation notes (2026-08-02)

### Classification (seven states, not a binary gap check)
`Void` (booklet's void_entries) → `Delivered` / `Partially Delivered` / `Self Pickup` (invoice's
`custom_delivery_status`) → `Pending Fulfillment` (invoice exists, still Pending/Not Delivered) →
`Reported, No Invoice` (report exists, no invoice - or a Confirmed report whose invoice isn't
ref-discoverable, see Todo 046's bug note) → `Unresolved` (nothing at all). `Partially Delivered`
is deliberately its own bucket, not folded into `Delivered` - prompted by the user asking how
partial delivery is currently handled; its eventual remainder is a follow-up confirm against the
*same* invoice; tracked by the ordinary reconciliation queue's own flagged-group clustering, not
by this checklist.

### Closing is hard-blocked, not advisory
`close_daily_reconciliation` recomputes the checklist fresh (never trusts what the frontend last
saw) and refuses if anything isn't in `{Void, Delivered, Partially Delivered, Self Pickup}` -
listing exactly which numbers are still open. Matches the user's own framing: "like daily account
book closing" - can't close the book with blank entries.

### Re-review is lazy, not a live push
`get_daily_reconciliation` is what actually detects drift: if a `Closed` record exists for the
date, it's compared against a fresh computation (range and all four summary counts) on every read;
on any difference, the record flips to `Needs Re-review` with a reason right there. There's no
background job watching for this - it surfaces the next time anyone opens that date, which is
sufficient for how this shop actually uses it (reconciled daily, so "the next time anyone looks"
is never far off).

### Live verification (bench console against hd.phirun.me)
Built a full realistic day: a driver-reported-and-confirmed delivery, a self-pickup backfill, a
still-pending invoice, a report-with-no-invoice, and a void page - confirmed every classification
was correct, that `close_daily_reconciliation` blocked on the unresolved ones and succeeded once
they were all resolved, that a late-arriving report after closing flipped the record to `Needs
Re-review` with an accurate reason, and that `reopen_daily_reconciliation` worked and preserved the
original `closed_by`/`closed_at` as history. All test data cleaned up (with the same few stubborn
$1 stock-locked test invoices noted in Todo 046 left behind, flagged to the user).
