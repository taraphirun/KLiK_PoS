## Decisions made with the user, 2026-08-03 (via AskUserQuestion + a mid-turn clarification)
- **Storage**: initially asked "new doctype vs. Warehouse custom fields vs. POS Profile field" and
  the user picked Warehouse custom fields - then clarified further: "pos profile is open per
  warehouse so select the address of those warehouse only." Since POS Profile already has a
  `warehouse` field (ERPNext core), this fully answered the "which warehouses count as a shop"

  and only if it's assigned to at least one *enabled* POS Profile.** Not every Warehouse is a shop

- **Address input**: manual latitude/longitude entry (not Google Places Autocomplete) - no

  one tied to the currently logged-in POS Profile/session - satisfies "I might need that to show
  up also" once more shops exist. Confirmed this matters: the map's delivery pins already aren't
  scoped to the active session's own POS Profile, so scoping shop pins to just the active profile
  would have been an inconsistent, single-location-only design that wouldn't have actually met the
  "more locations soon" ask.

## Design notes

### Visual distinction from delivery pins
`ShopMarker` uses Google's classic hosted pin sprite (`mapfiles/ms/icons/blue-dot.png` - a
teardrop shape) rather than the flat colored-circle `Symbol` every delivery cluster uses
(`STATUS_COLOR`: red/yellow/purple/green). Different *shape*, not just a different color, so a
shop pin reads as fundamentally different at a glance rather than risking confusion with a
delivery status. `zIndex={1000}` keeps shop pins on top of delivery clusters when they overlap.

### "Not configured" is `0`, not `NULL`
Float custom fields default to `0.0`, not `NULL`, when never touched - `get_shop_locations`
filters in Python (`if w.custom_shop_latitude and w.custom_shop_longitude`) rather than an `IS NOT
NULL` DB filter, which wouldn't actually exclude an unconfigured warehouse. A real `(0, 0)` shop
(the Gulf of Guinea) is implausible enough here to treat both falsy values as "not set yet."

## Addendum (2026-08-03, same-day follow-up)

### Map opens centered on the shop, not the delivery pins' average
User request: "make sure to open to around my warehouse location." `center` in
`LiveDeliveryMapPage.tsx` now prioritizes shop location(s) - averaging across all of them if
there's more than one - over the delivery pins' own average, which previously won regardless of
whether a shop was set. Falls back to the pin average, then `DEFAULT_CENTER`, only when no shop
location exists yet. Default zoom follows the same priority (14 when a shop exists, else 12/6).
"Recenter" already fit both pins and shop locations into its bounds (from the original pass), so
seeing everything together is still one click away - this only changes what loads by default.

### Custom shop pin icon
User asked for a specific Flaticon icon (a building silhouette inside a teardrop pin) instead of
the placeholder Google-hosted `blue-dot.png`. The link given was a Flaticon gallery page, not a
direct asset, and Flaticon's free tier requires attribution unless you have a paid subscription -
flagged this and asked how to proceed; user downloaded the file themselves and provided it
(`location.png`, 512x512 PNG) rather than having Claude build a from-scratch equivalent. Copied to
`klik_spa/public/shop-location-pin.png` (source) - same pattern as `bev_logo.jpeg`, both a
`klik_spa/public/` source copy and a `klik_pos/public/klik_spa/` build-output copy get committed,
since only `klik_pos/public/klik_spa/assets/` (the hashed JS/CSS bundle) and `index.html` are
gitignored, not top-level static files copied in from `klik_spa/public/`. `ShopMarker` references
it via `scaledSize`/`anchor` (40x40, anchored at bottom-center) so the pin's tip lands precisely on
the coordinate rather than the icon's raw 512x512 bounding-box center. Self-hosted, not hotlinked
to Flaticon - the licensing question (attribution) is the user's to resolve per Flaticon's terms
for this specific downloaded asset, not something this addendum resolves.

### Delivery cluster pins changed to a numbered pin shape (not the shop pin)
Clarified with the user: this request was about `ClusterMarker` (the existing delivery-cluster
markers, already counting/clustering nearby deliveries via `buildClusters`), not `ShopMarker` -
the shop pin from the previous addendum stays exactly as-is. "Live count" (confirmed via
AskUserQuestion, then clarified further) just means keep using `cluster.items.length` - already
computed fresh from `visiblePins` on every filter/realtime change, no backend work needed.

`ClusterMarker` swapped its flat `SymbolPath.CIRCLE` dot for a solid teardrop pin path (`PIN_PATH`,
same glyph family as lucide-react's `MapPin`, already used elsewhere on this page for visual
consistency) - same per-status fill color as before (`STATUS_COLOR`), count label repositioned
into the pin's bulge via `labelOrigin` instead of dead-center of a circle. Also changed: the count
label now always shows (including "1" for a single-delivery pin), not just for groups of 2+ - a
pin-shaped marker with no number would look inconsistent once its whole visual language became
"this is a count," so single-item pins now show "1" too. Flagging this as a judgment call in case
it's not wanted - easy to revert to the old isGroup-only label.

**Not verified in a browser** (same standing limitation this session) - the `anchor`/`labelOrigin`
coordinates are a reasoned best guess (Google Maps applies `scale` proportionally to both the path
and these points automatically, per the API's documented behavior), not confirmed by an actual
render. If the label looks off-center once viewed live, the fix is tuning `PIN_LABEL_ORIGIN`'s y
value (currently 9.5, in the pin's own 0-24 coordinate space) up or down.

### Live Feed: teleport-on-click + today-only default
Two more requests, same sitting:
- **Clicking a Live Feed item pans/zooms the map to it** - `MapFocuser` (new, rendered inside
  `<Map>` alongside `MapControls` purely to reach the raw map instance via `useMap()`) imperatively
  calls `map.panTo()` + `map.setZoom(17)` (only zooming *in*, never out, if already closer) when
  `focusTarget` changes. Deliberately imperative rather than switching `<Map>` to controlled
  `center`/`zoom` props - a controlled center would fight the user's own free panning on every
  re-render; an imperative one-off "jump there" (same pattern the existing "Recenter" control
  already uses) doesn't. Feed clicks still also open the cluster detail panel as before - this adds
  the pan/zoom on top, doesn't replace anything.
- **Live Feed defaults to today only** - a `todayOnly` toggle (default checked) inside
  `LiveFeedList` itself, not a change to the map's own `fromDate`/`toDate` filters (which stay
  default-empty/all-time) - scoped specifically to the feed per the user's wording ("for *that live
  feed*"). `isToday()` is deliberately permissive: a report with no `delivery_timestamp` yet (e.g.
  Unmatched, awaiting confirmation) is presumably very recent and stays visible rather than being
  hidden for lacking a stamp - only an actually past-dated timestamp excludes it.

Not verified in a browser (same standing limitation).

### Follow-up: zoom out, then back in ("get a feel of the relative location")
Plain `panTo`/`setZoom(17)` felt like a hard jump cut with no spatial context. Changed
`MapFocuser` to a three-step sequence: zoom out to an overview level (13, or wherever the map
already was if further out than that - never zooms *in* as the "out" step) → `panTo` the target
(animates smoothly on its own) → zoom back in to 17. Then the user asked to "make sure the zoom is
smooth" - the core Maps JS API's `setZoom()` has no built-in tween (unlike `panTo`, which already
animates), so `animateZoomTo()` (new) steps the zoom one level at a time on a 120ms timer as the
standard workaround, with a cancel function so a second Live Feed click before the first animation
finishes doesn't leave a stale timer racing the new one.

### Follow-up: stop reloading tiles on every click, even nearby ones
User reported the map looked like it kept "loading" between zooms, even for relatively close
locations. Root cause: the flyover unconditionally zoomed all the way out to level 13 and back to
17 on *every* click, regardless of whether the new target was already on-screen right next to the
previous one - each `setZoom()` step forces new tiles to load, so repeated nearby clicks looked
like constant reloading for no reason. Fixed two ways:
- `MapFocuser` now checks `map.getBounds()?.contains(target)` first - if the target is already
  visible and the map is already zoomed in reasonably close, it just does a plain smooth `panTo`
  (plus a small zoom-in only if not already close), skipping the zoom-out/in dance entirely. The
  full flyover only fires when the target is actually off-screen or the map is currently zoomed
  way out.
- `animateZoomTo` now steps 2 zoom levels at a time instead of 1 (`stepSize` param, default 2) when
  a flyover *is* warranted - halves the number of tile-reload events for the same zoom range.

### Follow-up: the real fix was map rendering technology, not animation tuning
User pushed back: preferred the original always-flyover behavior, just without the reload, and
asked to investigate whether map *type* was the cause before implementing anything - and to check
how the bot repo (`hd-delivery-telegram`) handles this, since its own live map already has smooth
zoom.

**Investigation**: confirmed map type is the root cause. This app's `<Map>` never set a `mapId`
(Todo 032 deliberately avoided it - "requires a Google Cloud 'Map ID' as a second required config
item beyond the API key"), so it renders classic **raster** tiles - discrete images per integer
zoom level, meaning any zoom change forces new tiles to load. No amount of step-size/timing tuning
in JS fixes that; it's a rendering-technology limit. The bot's own
`frontend/src/components/DeliveryMap.tsx` sets `mapId="fac5451902bae2bd765f0150"` (vector/WebGL
rendering, no discrete tiles) and drives its `flyTo()` via `requestAnimationFrame` calling
`map.moveCamera({center, zoom})` every frame with continuously-interpolated values - including a
parabolic zoom-out-then-in dip for any real distance (`distance > 5` **meters**, so it fires for
essentially any two distinct delivery points - this is why "always flyover" was actually their
default behavior, not a special case).

**Confirmed with the user** (AskUserQuestion) that adding a Map ID - a one-time Google Cloud
Console step, same project as the existing API key - was worth it for genuinely smooth zoom,
matching their own bot's UX.

**Implemented**:
- `klik_pos/setup/install.py` - `ensure_google_maps_api_key_field()` extended (now via
  `create_custom_fields`, `update=True` default) to also add `custom_google_maps_map_id` (Data,
  optional - the map still renders without it, just stays raster) on POS Profile.
- `klik_spa/src/stores/posProfileStore.ts` - `POSProfile` interface gains explicit
  `custom_google_maps_api_key?: string` and `custom_google_maps_map_id?: string`. Bonus: this
  actually **fixed a pre-existing tsc error** that's shown up in every baseline check this
  session (`Type '{}' is not assignable to type 'string'` at `<APIProvider apiKey={apiKey}>`) -
  `custom_google_maps_api_key` was never explicitly typed, so it fell through `POSProfile`'s
  `[key: string]: unknown` index signature as `unknown` instead of `string`. tsc error count is
  now 187, down from the known 188 baseline.
- `klik_spa/src/pages/LiveDeliveryMapPage.tsx` - `MapFocuser` rewritten to port the bot's `flyTo()`
  algorithm exactly (same duration formula, same parabola/`zoomOutAmount` formula, reusing this
  file's own `haversineMeters` in place of their `calculateDistance` - identical formula, just
  already present here). `<Map mapId={mapId || undefined}>` wired from the new POS Profile field.
  Removed `animateZoomTo`/the discrete step-based approach entirely, along with the "skip if
  already visible" optimization from the previous attempt (no longer needed or wanted - the user
  explicitly preferred always-flyover).

**Verified**: both Custom Fields exist after `bench migrate`. `npx tsc --noEmit -p
