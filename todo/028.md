# Todo 028: Migrate `delivery_driver` Free-Text → `Link(Delivery Driver)`

**Status:** ✅ Done

## Description
Convert the free-text driver fields introduced in Phase 9 to proper `Link` references now that a
`Delivery Driver` master exists (Todo 025), and backfill existing free-text values by matching them to
driver records.

## Estimated Time
1-2 hours

## Files to Change
- `klik_pos/klik_pos/doctype/delivery_report/delivery_report.json` (MODIFY — `delivery_driver`
  Data → Link(Delivery Driver))
- `klik_pos/klik_pos/custom/sales_invoice.json` (MODIFY — `custom_delivery_driver` Data →
  Link(Delivery Driver))
- `klik_pos/klik_pos/patches/` (New patch to backfill + a `patches.txt` entry)
- Update auto-match (Todo 022) and reconciliation write-back (Todo 023) to resolve/assign the
  driver Link instead of a raw string.

## Migration Strategy
- Add the `Link` fields alongside the existing text (or convert in place) and run a data patch:
  for each existing `delivery_driver` string, find a `Delivery Driver` by `driver_name` (case-insensitive)
  or Telegram identity; link if found, else leave blank and log for manual review.
- Restrict the Link with a filter to `status = Active` so rejected/pending drivers aren't selectable.

## Acceptance Criteria
- New Delivery Reports and Sales Invoices reference a `Delivery Driver` record, not free text.
- The backfill patch runs idempotently and reports how many rows linked vs. left unmatched
  (no silent drops — log the unmatched, per project convention).
- Auto-match and reconciliation set the driver Link correctly end-to-end.
- Existing data is preserved; unmatched free-text values remain visible for manual fixing.

## Dependencies
- Todo 025 (Delivery Driver DocType), and Phase 9 Todos 019/020/022/023 must exist first.

## Risks
- Changing a field's type from Data to Link in Frappe can require the stored value to be a valid
  Delivery Driver `name`; do the backfill in the same patch that changes the type, or stage via a new field
  then drop the old one.
- Free-text typos won't all match — accept a manual-review remainder rather than forcing bad links.

## Implementation notes (2026-07-30)

### Design deviation: staged via a new field, not converted bare in place
The Migration Strategy note and Acceptance Criteria were in tension as written: "leave blank ...
for manual review" (Migration Strategy) vs. "unmatched free-text values remain visible for manual
fixing" (Acceptance Criteria) - a bare Data-to-Link conversion can't do both, since an unmatched
Link field has nowhere to hold the original text once it's expected to hold a real docname.
Resolved by adding a companion field on each doctype instead of converting bare:
- **Delivery Report**: `delivery_driver` is now the resolved `Link(Delivery Driver)` (blank if
  unmatched). New `reported_driver_name` (Data) holds the bot's verbatim text, always populated
  regardless of match outcome - this is what satisfies "remain visible for manual fixing." New
  `delivery_driver_name` (Data, `fetch_from: delivery_driver.driver_name`, read-only) gives a
  human-readable display value without a client-side join, mirroring this codebase's existing
  `custom_delivery_personnel` / `custom_delivery_personnel_name` pattern exactly (Todo 020 already
  established this convention - reused it rather than inventing a new one).
- **Sales Invoice**: `custom_delivery_driver` is now `Link(Delivery Driver)`. New
  `custom_delivery_driver_name` (fetch_from) added the same way. No separate "reported" field
  needed here - `custom_delivery_driver` was always just a copy of the (already-preserved)
  Delivery Report value, never independently bot-reported.
- `link_filters: [["Delivery Driver","status","=","Active"]]` added to Delivery Report's
  `delivery_driver` field only (Todo 025's Active-only Acceptance Criterion) - it's the one Link
  field a human can actually edit via re-match; Sales Invoice's copy is `read_only`, so a Desk UI
  dropdown filter there would never be shown.

### Driver resolution logic (`klik_pos/api/delivery.py::resolve_driver`)
Extracted as a standalone function (not folded into `match_delivery_report`, despite the todo
title referencing "auto-match/Todo 022") since it resolves a *driver*, not an *invoice* - a
separate axis with separate signals. Telegram id first (unique, bot-verified via
`sync_driver_from_bot`, Todo 026), else an exact `driver_name` match (case-insensitive is free
under Frappe's default DB collation - no need for the fuzzy/normalized tiers `match_delivery_report`
uses for invoices). Deliberately **no fuzzy fallback**: a wrong invoice match gets caught by a
human looking at the invoice before confirming; a wrong driver link has no equivalent
reconciliation-blocking symptom, so returning `None` (leave blank, let a human pick it) beats
guessing. Known limitation, not fixed: a duplicate `driver_name` across two Delivery Driver records
resolves to whichever `frappe.db.get_value` happens to return first - acceptable since
`driver_name` isn't unique by design (Todo 025) and this is a soft link, not an identity key.

Wired into ingestion (`submit_delivery_report`, Todo 021): now sets both `reported_driver_name`
(raw) and `delivery_driver` (resolved) at insert time, so newly-ingested reports never land with
free text sitting in the Link column. `confirm_delivery_match` (Todo 023) needed **no logic
change** - `invoice.custom_delivery_driver = report.delivery_driver` was already just copying one
field to another; both sides being Link now makes that assignment type-correct instead of
free-text-to-free-text, with zero code change.

### Backfill patch (`klik_pos/patches/v16_0/backfill_delivery_driver_links.py`, post_model_sync)
Two phases, matching the field dependency: Delivery Report first (its `delivery_driver` becomes
the source of truth), then Sales Invoice. For Sales Invoice, rows with a `custom_delivery_report`
Link **copy that report's now-resolved `delivery_driver`** rather than independently re-running
`resolve_driver` - guarantees the two fields can't disagree, since `custom_delivery_driver` was
always derived from the report in the first place (Todo 023). Independent matching is only a
defensive fallback for a `custom_delivery_driver` row with no linked report (not expected to occur
given current code paths, but handled rather than assumed impossible). Idempotent: a
Delivery Report with `reported_driver_name` already populated, or a Sales Invoice whose
`custom_delivery_driver` already resolves to itself, is skipped on a re-run. Prints a summary count
(`N linked / M unmatched`) per doctype, per the Acceptance Criteria's "report how many rows linked
vs. unmatched."

### Verification
- Both schema changes applied via `bench migrate` cleanly (Data/Link share the same underlying
  `varchar(140)` column, so no destructive DDL) - confirmed via `information_schema.columns` and
  `Custom Field`/`DocField` metadata (`fieldtype: Link`, `options: Delivery Driver` on both sides).
- This site had **zero** existing `delivery_driver`/`custom_delivery_driver` rows (confirmed by
  direct count before starting - Phase 9 was only ever exercised with synthetic data that was
  cleaned up each time), so the real backfill run was a 0/0 no-op. Patch logic itself was verified
  separately: inserted three raw pre-migration-shaped rows directly via SQL (bypassing Link
  validation, to simulate genuine old data) - one matching by `driver_telegram_id`, one by exact
  `driver_name`, one deliberately unmatched - then called `_backfill_delivery_reports()` directly.
  Result: 2 linked / 1 unmatched, matched IDs correct, unmatched row left `delivery_driver` blank
  with `reported_driver_name` preserved. Re-running produced 0/0 (idempotent). Cleaned up
  afterward.
- Full patch also re-run through the real `bench migrate` pipeline (not just the direct function
  call) after being added to `patches.txt` - completed with a `Patch Log` entry, no errors.
- End-to-end ingestion-to-confirmation flow verified via `bench execute` against a real submitted
  invoice (`ACC-SINV-2026-00021`, fully paid so no Payment Entry side effect): created an Active
  Delivery Driver, called `submit_delivery_report` (verified it resolved `delivery_driver` via
  Telegram id and auto-matched the invoice), then `confirm_delivery_match` (verified
  `custom_delivery_driver` and the fetched `custom_delivery_driver_name` landed correctly on the
  invoice). All test data cleaned up afterward (invoice fields reset, driver and report deleted).
- Frontend: `DeliveryReport` type (`delivery.ts`) and `DeliveryReconciliationPage.tsx`'s
  `ReportCard` updated to display `delivery_driver_name || reported_driver_name` instead of the
  now-cryptic `delivery_driver` docname, plus an "unlinked" badge when a report has bot-reported
  text but no resolved driver. Not itemized in the original Files to Change, but required - the
  reconciliation page (Todo 024) was reading `delivery_driver` as a display string, which the
  Link migration silently breaks otherwise (renders a docname like "DRV-0001" instead of a name).
  `npx tsc --noEmit` and `yarn build` both clean.
