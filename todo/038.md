# Todo 038: Create Sales Invoice from Delivery Reconciliation

**Status:** ✅ Done (backend verified live end-to-end against the real KlikPOS site; frontend
build/typecheck clean, not yet browser-checked - see notes)

## Description
Add a "Create Invoice" action to Unmatched rows on the Delivery Reconciliation page for the paper
→ ERPNext transition period, where a reported delivery has no corresponding Sales Invoice yet. A
lightweight modal (customer picker + item table) lets staff enter what's on the paper slip and
create+submit the Sales Invoice, then immediately links it to the Delivery Report and posts
payment through the existing confirm flow — one create action instead of switching to POS,
checking out, then coming back to reconcile.

## Estimated Time
3-4 hours

- `klik_pos/api/sales_invoice.py` (MODIFY — optional `posting_date` passthrough)
- `klik_pos/api/delivery.py` (NEW — `create_invoice_from_delivery_report`)
- `klik_spa/src/services/delivery.ts` (MODIFY — new service call)

## Requirements

### Backend
- `_set_posting_fields(doc, posting_date=None)`: use `posting_date` (split into date/time) when
  given, else current behavior (`nowdate()`/`nowtime()`). Threaded through
  `build_sales_invoice_doc(..., posting_date=None)` → `parse_invoice_data` (reads
  `data.get("posting_date")`) → `queue_sales_invoice`. No caller changes required for the existing
  POS checkout flow (it never sends this key).
- `create_invoice_from_delivery_report(report_name, invoice_data)`:
  - Load the `Delivery Report`; throw if `reconciliation_status == "Confirmed"` (already linked to
    a real invoice — use the normal re-match flow instead, not this).
  - `invoice_data` is the same shape `queue_sales_invoice` already expects (`customer`, `items`,
    optional `posting_date`, payment fields) — call `sales_invoice.queue_sales_invoice(invoice_data)`
    directly (Python call, reuse the full tax/stock/payment engine unchanged).
  - On success, call the existing `confirm_delivery_match(report_name,
    invoice_name=result["invoice_name"])` to stamp delivery fields onto the new invoice and post
    the Payment Entry if the report's `payment_status` warrants it — no duplicate logic.
  - Return the combined result (invoice name + confirm result) or the first failure, whichever
    happened.

### Frontend
- `CreateInvoiceFromReportModal`: opens from an Unmatched row's "Create Invoice" button.
  - Customer: `CustomerSearchSection` (controlled, local `useState<Customer|null>`) — reused as-is,
    inline customer creation comes for free.
  - Items: simple add/remove row table (item search via `useProductStore` — the same store the
    POS grid already uses when a session is active — + qty + rate), not the full POS cart UI.
  - Posting date: date input, prefilled from `report.delivery_timestamp`, editable.
  - Submit disabled until customer + at least one item with qty>0 and rate>=0 are set (mirrors
    `parse_invoice_data`'s own validation, so the modal fails fast instead of round-tripping).
  - On success: close modal, refresh the reconciliation list, surface the new invoice name.
- Reconciliation list: show "Create Invoice" only on rows where `reconciliation_status ==
  "Unmatched"` (a `Suggested` row already has a real invoice to confirm against instead).

## Acceptance Criteria
- Creating an invoice from a paper-only delivery works end to end: invoice created+submitted with
  the entered items/customer, stock deducted, `posting_date` reflects the delivery date (not
  today, unless staff changed it), and the Delivery Report flips to `Confirmed` with
  `matched_invoice` set and (if applicable) a Payment Entry posted — identical end state to
  confirming against a pre-existing invoice.
- Normal POS checkout (`queue_sales_invoice` called without `posting_date`) is unaffected —
  `posting_date` still defaults to today.
- `npm run build` (klik_spa) and `python3 -m py_compile` (backend) both pass.

## Dependencies
- Module 10 (`confirm_delivery_match`, `Delivery Report`) and Module 6 (`queue_sales_invoice`,
  `create_payment_entry`) — both reused unchanged apart from the `posting_date` addition.

## Risks
- Backdated stock deduction on a `posting_date` earlier than other already-submitted invoices/
  stock ledger entries can produce negative-stock validation errors depending on Item settings —
  staff may need to adjust opening stock separately if the transition-era backlog is large; not
  something this feature can resolve on its own.
- Requires an active POS Opening Entry (per the decision to keep pricing/tax/warehouse resolution
  POS-Profile-bound) — a back-office user with no open shift can't use this until one is open.

## Implementation notes (2026-08-01)

### Backend
- `_set_posting_fields(doc, posting_date=None)` now accepts an optional override, threaded through
  `build_sales_invoice_doc(..., posting_date=None)`. `queue_sales_invoice` reads
  `data.get("posting_date")` directly from its own `data` argument (normalized to a dict first if
  the client sent a JSON string — matches how `parse_invoice_data` already handles that case) —
  deliberately NOT threaded through `parse_invoice_data`'s return tuple, which has 5 other call
  sites that don't need this and would all have needed their unpacking updated for no reason.
- `create_invoice_from_delivery_report(report_name, invoice_data)` (`klik_pos/api/delivery.py`):
  throws if the report is already `Confirmed`; forces `enable_background_submission=False` on the
  incoming payload before calling `queue_sales_invoice` (background-queued invoices stay
  `docstatus=0` until an async job submits them — `confirm_delivery_match` requires `docstatus=1`
  immediately, so this has to be synchronous). Calls the existing `confirm_delivery_match`
  unchanged to link + post payment; if that step fails after the invoice was already created, the
  invoice is left as-is (not rolled back) and the response points staff at re-match to link it
  manually rather than silently discarding a real submitted invoice.

### Live verification (bench execute against hd.phirun.me, all test data cleaned up after)
Created a real Unmatched Delivery Report via `submit_delivery_report`, then called
`create_invoice_from_delivery_report` against it twice:
1. With `posting_date` backdated to `2026-07-15` on an item whose current stock was all received
   *after* that date → correctly failed with ERPNext's own insufficient-stock-as-of-date error
   (`_validate_reserved_stock_for_items`). This is a real, expected consequence of the "stock
   deducted normally, no bypass" decision, not a bug — flagged prominently to the user rather than
   silently working around it. Backdating to a date before an item's stock was actually received
   will hit this for any item, not just ones genuinely out of stock today.
2. Without a `posting_date` override (defaults to today) → succeeded end-to-end: created and
   submitted `ACC-SINV-2026-00032`, linked it to the Delivery Report (`reconciliation_status` →
   `Confirmed`), `custom_delivery_status`/`custom_delivered_at`/`custom_delivery_report` stamped
   correctly. Cleaned up (cancelled + deleted the invoice and the test Delivery Report) afterward.

### Frontend
- `CreateInvoiceFromReportModal.tsx`: customer via reused `CustomerSearchSection` (inline
  customer-creation comes for free via its existing `AddCustomerModal` integration — no new
  backend work needed for that decision); items via a local, independent search against
  `klik_pos.api.item.item_listing.get_items` — deliberately NOT `useProductStore`, which is the
  same global singleton state the live POS product grid reads/writes; reusing it here would
  overwrite what a cashier sees on the POS screen if used concurrently with an open shift
  elsewhere in the app. Posting date input defaults via `defaultPostingDate()` from
  `report.delivery_timestamp`, editable.
- `DeliveryReconciliationPage.tsx`: "Create Invoice" button added to `ReportCard`'s action row,
  gated on `!report.matched_invoice && !isResolved` (a `Suggested` row already has a real invoice
  to confirm against, so the backfill action would be redundant there).
- `npm run build` and `npx tsc --noEmit` both clean.

## Follow-up (2026-08-01): item-code bug fix + payment status / due date (Todo 039 territory)

Two real issues found by the user actually using the feature, both fixed and live-verified:

### Item-code bug
`get_items`'s response shape is `{id: item_code, name: display_name, ...}` — the *opposite* of a
naive DB-row convention. The modal had it backwards (`item.name` used as item_code), so picking
"AZT" sent its Khmer display name as the item code, and the backend correctly rejected it ("Item
3c បុិច not found"). Fixed in `CreateInvoiceFromReportModal.tsx` (`ItemSearchResult.id` is now the
code, `.name` the display).

### Payment status + due date
User hit ERPNext's own credit-limit check on submit ("expected", per the user — not something to
bypass) and asked for a way to declare payment status (and a due date when not paid) from the
modal, rather than every backfill invoice defaulting to fully-outstanding.

- `queue_sales_invoice` (`klik_pos/api/sales_invoice.py`) gained an opt-in `pay_in_full` flag: sets
  `amount_paid = doc.grand_total` once tax is known (can't be pre-computed client-side - the modal
  has no live tax preview) and appends/updates a payment row using the POS Profile's default
  payment mode. Two non-obvious things this needed, both discovered by testing live rather than
  assuming success:
  1. `doc.is_pos` is decided by `_set_pos_profile_fields` from `amount_paid` *as it stood when
     `build_sales_invoice_doc` was called* - which is 0 for pay_in_full (the whole point is not
     knowing the amount yet). A non-POS invoice always submits with `paid_amount=0` regardless of
     what's assigned afterward, so `pay_in_full` has to also force `doc.is_pos = 1`, not just set
     `paid_amount`/`payments`.
  2. ERPNext's credit-limit check (`SalesInvoice.check_credit_limit`) runs from `on_submit`,
     *after* `make_gl_entries()` - so it sees this invoice's own outstanding at submit time. A
     Payment Entry posted afterward (confirm_delivery_match's normal mechanism) is a separate
     transaction and doesn't help; payment has to be baked into the same submission.
- `create_invoice_from_delivery_report` gained `payment_status` / `amount_collected` / `due_date`
  params. Shapes `invoice_data` per status (`Paid` → `pay_in_full`; `Partial` → explicit
  `amountPaid`/`paymentMethods` with the resolved default mode; `Unpaid` → `isCreditSale` +
  required `dueDate`), writes the chosen status back onto the Delivery Report (so the record
  reflects what staff actually declared, not whatever was originally reported), and always calls
  `confirm_delivery_match(..., mark_paid=False)` - payment is already baked into the invoice's own
  submission, so a second Payment Entry from confirm's own posting path would double it up.
  Also defaults `businessType` to `"B2C"` when the caller doesn't set it (same is_pos root cause).
- Live-verified all three paths against the real site (bench execute, all test data cleaned up
  after): Paid → `paid_amount == grand_total`, `outstanding_amount == 0`, `is_pos == 1`; Partial →
  correct split (paid 3.0 of 7.8, outstanding 4.8) with due date set; Unpaid → standard credit sale,
  full amount outstanding, due date set. Delivery Report's `payment_status`/`amount_collected`
  confirmed updated to match in all three cases.
- Frontend: `CreateInvoiceFromReportModal.tsx` gained a Payment Status select (Paid/Partial/
  Unpaid), an Amount Collected input (Partial only), and a Due Date input (shown whenever status
  isn't Paid). `delivery.ts`'s `createInvoiceFromDeliveryReport` now takes `paymentStatus`,
  `amountCollected`, `dueDate`. `npm run build` and `npx tsc --noEmit` both clean.

### Still not yet done
Browser click-through of the modal (unchanged from above) — this pass added backend live
verification for all three payment paths, but the modal's own UI still hasn't been driven in a
real browser.
