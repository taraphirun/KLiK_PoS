# Todo 019: `Delivery Report` Staging DocType

**Status:** ⬜ Not started

## Description
Create a new DocType that stores raw, untrusted delivery data submitted by the Telegram
delivery bot, plus the reconciliation state that tracks how it maps to a real Sales Invoice.
This is the staging layer — records here never affect accounting until confirmed.

## Estimated Time
1-2 hours

## Files to Change
- `klik_pos/klik_pos/doctype/delivery_report/delivery_report.json` (New)
- `klik_pos/klik_pos/doctype/delivery_report/delivery_report.py` (New)
- `klik_pos/klik_pos/doctype/delivery_report/__init__.py` (New)

## Fields
Field set mirrors the bot's authoritative `delivery_logs` record (see
`hd-delivery-telegram/delivery-bot/bot.py`) plus the KlikPOS-side reconciliation state.

**From the bot (as collected via the aiogram FSM flow):**
- `bot_delivery_id` (Data, unique) — the bot's row UUID; the **idempotency key** for ingestion/sync
- `reported_invoice_no` (Data) — invoice number the driver typed (may be wrong)
- `completion_status` (Select: Full / Partial) — "All Delivered" / "Missing Product"
- `payment_status` (Select: Paid / Unpaid / Partial) — driver-reported collection state
- `gps_latitude` (Float), `gps_longitude` (Float) — from Telegram location share
- `delivery_driver` (Data — free text for now; see Design Note)
- `driver_telegram_id` (Data) — bot `driver_id` (Telegram user id)
- `delivery_timestamp` (Datetime)
- `photos` (Attach / child table of file URLs) — from `photo_file_ids`, uploaded on sync
- `voice_note` (Attach) — from `voice_note_file_id`, uploaded on sync

**KlikPOS reconciliation state (set here, not by the bot):**
- `matched_invoice` (Link → Sales Invoice) — the reconciled invoice, set on match/confirm
- `amount_collected` (Currency) — for Partial payment reconciliation (derived/confirmed in KlikPOS)
- `reconciliation_status` (Select: Unmatched / Suggested / Confirmed / Rejected) — default Unmatched
- `match_confidence` (Percent or Float 0–1) — set by auto-match (Todo 022)
- `payment_entry` (Link → Payment Entry) — set if mark-as-paid posted a payment
- `raw_payload` (JSON/Code) — full original bot payload for audit

> Note: `payment_status` replaces the earlier `paid_at_location` checkbox — the bot already gives
> a richer Paid/Unpaid/Partial value. The mark-as-paid trigger (Todo 023) keys off this field.

## Design Note: driver is free text — decided
`delivery_driver` is a plain `Data` field for now. Driver create/approve/management is handled in
**Phase 10 (Module 11)**, which introduces a `Driver` doctype and migrates this field to a `Link`
in Todo 028. Keep matching (Todo 022) tolerant of free-text driver names so that later migration
is non-breaking.

## Acceptance Criteria
- DocType installs cleanly (`bench migrate` / fixture load) with no schema errors.
- `reconciliation_status` defaults to `Unmatched` on insert.
- A unique constraint on `bot_delivery_id` makes ingestion idempotent — the bot's offline sync
  worker (Phase 13) can safely re-send the same delivery without creating a duplicate.
- `completion_status` and `payment_status` accept exactly the bot's enum values (Full/Partial and
  Paid/Unpaid/Partial) so no data is dropped on ingest.
- `raw_payload` preserves the untouched original bot data even after fields are edited.

## Dependencies
- None (foundational for the rest of Phase 9)

## Risks
- Free-text driver names invite typos/duplicates ("John" vs "john d."); keep Todo 022 matching
  case-insensitive and be ready to migrate to a Link once the driver master exists.
- Idempotency must key on `bot_delivery_id` (stable per delivery), never on invoice number — a
  driver can legitimately log several deliveries against related invoices.
