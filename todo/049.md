# Todo 049: Self-Pickup Checkbox at POS Checkout

**Status:** ✅ Done

## Description
Follow-up to Module 17 ([phase-16.md](../phases/phase-16.md)): the Daily Reconciliation page's
"Confirm Self-Pickup" action only helps after the fact. When a customer is standing at the counter
buying something and taking it immediately, forcing a trip to Daily Reconciliation afterward to
mark something already known is pure friction. Adds a checkbox to POS checkout that sets
`Self Pickup` on the invoice at submission time instead.

## Files Changed
- `klik_pos/api/sales_invoice.py` - `parse_invoice_data`/`build_sales_invoice_doc` gain a
  `self_pickup` flag; wired through all 5 call sites that unpack `parse_invoice_data` (checkout,
  both pre-submit preview/validation paths, hold-order draft creation, and draft resume/submit -
  `_update_existing_draft_invoice`'s own internal rebuild deliberately excluded, see notes)
- `klik_spa/src/components/dialog/PaymentDialog.tsx` - "Customer picking up now" checkbox next to
  the existing Delivery Personnel picker, mutually exclusive with it, wired into `buildPaymentData`

## Implementation notes (2026-08-02)

### `parse_invoice_data`'s return tuple has five call sites, not one
Adding a new element to `parse_invoice_data`'s return tuple meant every unpacking site needed
updating in lockstep or the whole checkout/validation/draft system would break with "too many
values to unpack": `validate_checkout_invoice`, `validate_before_submit`, `queue_sales_invoice`,
`create_draft_invoice`, and `submit_draft_invoice`. Found and fixed all five; `build_sales_invoice_doc`
itself is also called from all but one of those (`create_draft_invoice`'s "update an existing held
order" branch goes through `_update_existing_draft_invoice` instead) - `self_pickup=self_pickup`
threaded through each. `submit_draft_invoice` additionally needed the same
`rebuilt_doc → invoice_doc` field-copy treatment `custom_invoice_ref` already gets, since that
function assembles the final submitted doc field-by-field rather than using the freshly-built one
directly.

### `_update_existing_draft_invoice` deliberately not wired
That function (used when re-holding an already-held order) has its own separate parameter list and
calls `build_sales_invoice_doc` internally - reachable only from the "hold order" frontend flow,
which never sends `selfPickup` (self-pickup isn't meaningful for an order that isn't finalized
yet). Left its signature untouched rather than plumbing an always-`False` parameter through for no
behavioral gain.

### Mutual exclusivity is UI-only, not backend-validated
Checking the box clears `selectedDeliveryPersonnel` in the frontend and hides the picker; the
backend doesn't reject a payload with both set. Matches this codebase's existing posture elsewhere
(e.g. `set_manual_delivery_status`'s guard is the only backend-side mutual-exclusivity check in
this module) - not worth a second one here for a UI-enforced case.

### Live verification (bench console against hd.phirun.me)
`queue_sales_invoice` with `selfPickup: true` correctly set `custom_delivery_status = "Self
Pickup"` and stamped `custom_delivered_at`; a normal call without the flag still defaults to
`Pending` (regression check). Both test invoices cleaned up after.

### Real bug found by the user: checkbox never rendered
First browser check showed neither the new checkbox nor the pre-existing Delivery Personnel picker
in the payment dialog at all. Root cause: the checkbox was nested inside the same
`{isDeliveryRequired && (...)}` block as the Delivery Personnel picker, and both POS Profiles on
`hd.phirun.me` (`Sale Test`, `Phirun`) have `custom_delivery_required = 0` - so that whole block
never rendered, hiding both. Self-pickup isn't conditional on that flag (it's a standalone "how was
this order fulfilled" choice, not an alternative only relevant when delivery is otherwise
mandatory) - fixed by pulling the checkbox out of that gate entirely so it always shows; the
Delivery Personnel picker itself stays gated on `isDeliveryRequired && !isSelfPickup`. Frontend-only
fix (`npm run build`), no backend change, no `k_reset` needed - just a browser reload.
