# Todo 030: Conflicts / Duplicates View

**Status:** ❌ Dropped (2026-07-31) — Module 12 dropped, see phases/phase-11.md. The "duplicate
`reported_invoice_no`" conflict type this todo specified was itself wrong: a single invoice can
legitimately have multiple real Delivery Reports (partial, then the remainder) — see phase-09.md's
addendum for how that's handled instead.

## Description
A native KlikPOS view that surfaces delivery reports needing human attention — duplicates and
low-confidence/unmatched matches — the equivalent of the bot's `conflicts/duplicates` and
`low-confidence` screens, but operating on Frappe `Delivery Report` records.

2-3 hours

- `klik_spa/src/pages/DeliveryConflictsPage.tsx` (New)

## Conflict types
- **Duplicates**: multiple Delivery Reports with the same `reported_invoice_no` (or matched to the
  same Sales Invoice) — driver logged the same delivery twice, or two drivers claim it.
- **Low confidence / unmatched**: `reconciliation_status` = Unmatched, or Suggested with
  `match_confidence` below a threshold.

## Requirements
- Group duplicates together; let the user keep one and reject the others (routes to Phase 9
  reject/confirm endpoints).
- For low-confidence, show the suggested invoice + why, with confirm / re-match / reject.
- Badge/count on the nav so the backlog is visible.

## Acceptance Criteria
- Duplicate groups are detected correctly and resolving one updates the group.
- Confirming/rejecting here never double-posts payments (relies on Todo 023 idempotency).
- `npm run build` passes.

## Dependencies
- Phase 9 (Todos 022, 023), Todo 029 (shared components)

## Risks
- Duplicate detection heuristics can be noisy — make the grouping rule explicit and reviewable,
  and log/showcase what was grouped rather than auto-resolving.
